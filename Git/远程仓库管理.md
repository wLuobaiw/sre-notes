# 核心概念

## 远程仓库的本质

远程仓库是托管在**网络服务器**上的 Git 版本库副本（与本地仓库结构相同）。它用于**备份代码**、**多人协作**和**持续集成 / 持续部署**。本地仓库与远程仓库通过 `push` / `pull` / `fetch` 等命令同步数据。

## origin —— 默认远程仓库名称

`origin` 是 Git 的**默认约定**名称。当你克隆一个远程仓库时，Git 自动将源仓库命名为 `origin`，你可以通过 `-o` 或 `--origin` 自定义名称。

## 本地分支 vs 远程跟踪分支

| 类型 | 名称示例 | 说明 |
| :--- | :--- | :--- |
| 本地分支 | `main`、`feature-login` | 你正在编辑、提交的分支，存储在本地 `.git` 中 |
| 远程跟踪分支 | `origin/main`、`origin/feature-login` | 本地对远程仓库分支状态的**只读快照**，由 `git fetch` 更新 |
| 上游分支 | `origin/main` 是本地 `main` 的上游 | 定义了本地分支与远程分支的**跟踪关系** |

> **注意**
>
> 1. 远程跟踪分支（`origin/main`）指向的是**上次与远程仓库通信时的状态**，并非实时的远程仓库最新状态
> 2. 你**不能直接切换到远程跟踪分支**并提交，只能基于它创建新的本地分支
> 3. 远程跟踪分支在本地不可修改，只能通过 `git fetch` 同步

## 协作工作流图示

```
                            远程仓库 (GitHub/Gitee/GitLab)
                                   |
                          ┌────────┴────────┐
                          |                 |
                        git push          git fetch / git pull
                          |                 |
                    ┌─────┴─────┐    ┌──────┴──────┐
                    |  本地仓库  |    |   本地仓库   |
                    | (推送者)   |    |  (拉取者)    |
                    └───────────┘    └─────────────┘
```

详细协作流程：

```
 开发者 A                       远程仓库                       开发者 B
    |                              |                              |
    |--- git push -u origin main → |                              |
    |                              |--- (远程 main 已更新) ---→   |
    |                              |←--- git pull origin main --- |
    |                              |                              |
    |            多人同时推送时：                                  |
    |--- git push → 被拒绝 (非快进)                                |
    |--- git pull --rebase (合并远程更新)                         |
    |--- git push (推送成功)                                      |
    |                              |                              |
```

# git clone

用于将远程仓库**完整克隆**到本地（自动初始化本地仓库、添加远程关联、下载所有提交历史并检出默认分支）。

```bash
git clone [选项] <仓库地址> [本地目录名]
```

**选项**

- **-b, --branch <分支名>**：克隆完成后自动检出指定分支（而不是远程仓库的默认分支）
- **--depth <N>**：浅克隆，只拉取最近 N 层提交历史（节省时间和空间，适合 CI/CD 或只需最新代码的场景）
- **--single-branch**：仅克隆指定分支的历史，不拉取远程其他分支的引用信息
- **--recurse-submodules**：克隆主仓库后，递归初始化并更新所有子模块
- **--shallow-submodules**：对子模块也使用浅克隆（配合 --recurse-submodules 使用）
- **-c <key=value>**：克隆前设置一次性的 Git 配置项（如 `-c http.proxy=xxx`）
- **--config <key=value>**：等同于 `-c`，将配置写入克隆后仓库的 `.git/config`
- **-o, --origin <名称>**：自定义远程仓库的本地名称（默认值为 `origin`）
- **--bare**：创建裸仓库（只包含版本库数据，无工作区，用于服务器搭建）
- **--mirror**：创建远程仓库的完整镜像（包含所有分支、标签、引用，用于仓库迁移）
- **-v, --verbose**：显示详细输出信息
- **--progress**：强制显示进度报告（默认在终端中显示）

> **注意**
>
> 1. 仓库地址支持 HTTPS（`https://github.com/user/repo.git`）和 SSH（`git@github.com:user/repo.git`）两种协议 —— HTTPS 适合初学者（不需要配置 SSH 密钥），但每次推送需输入账号密码；SSH 需提前配置公钥，配置后免密操作
> 2. 省略 `[本地目录名]` 时，Git 会以远程仓库名为目录名（如 `git clone https://github.com/user/my-app.git` 会在当前目录创建 `my-app/` 文件夹）
> 3. 浅克隆后的仓库可以通过 `git fetch --unshallow` 补全完整历史
> 4. 克隆已有提交历史的仓库时，如果网络不稳定可加 `--depth 1` 快速下载
> 5. Windows 上克隆仓库时要注意路径长度限制（Windows 最大路径 260 字符），Git for Windows 提供了 `core.longpaths true` 配置绕过此限制
> 6. `git clone` 会自动设置远程跟踪分支，无需手动执行 `git remote add`

**示例**

```bash
# 基本克隆（HTTPS 方式）
git clone https://github.com/user/project.git

# 基本克隆（SSH 方式，需提前配置 SSH 密钥）
git clone git@github.com:user/project.git

# 克隆指定分支并重命名本地目录
git clone -b develop https://github.com/user/project.git my-project

# 浅克隆（只拉取最近 1 次提交）
git clone --depth 1 https://github.com/user/project.git

# 单分支浅克隆（最快方式）
git clone --depth 1 --single-branch -b main https://github.com/user/project.git

# 克隆并自定义远程仓库名称（不叫 origin）
git clone -o upstream https://github.com/user/project.git

# 克隆包含子模块的项目
git clone --recurse-submodules https://github.com/user/project.git
```

# git remote

用于**管理**本地仓库关联的远程仓库（查看、添加、修改、删除远程仓库关联）。

```bash
git remote [选项] [子命令]
```

**子命令**

- **无参数**：列出当前仓库关联的所有远程仓库简称（每行一个）
- **-v**：显示所有远程仓库的简称和对应的完整 URL 地址
- **add <简称> <地址>**：为本地仓库添加一个新的远程仓库关联
- **remove <简称>**：解除与指定远程仓库的关联（删除远程仓库记录）
- **rename <旧名> <新名>**：重命名一个已存在的远程仓库简称
- **set-url <简称> <新地址>**：修改指定远程仓库的 URL 地址
- **show <简称>**：显示远程仓库的详细信息（包括分支跟踪关系、fetch/push URL 等）
- **prune <简称>**：清理本地仓库中指向远程已删除分支的引用（垃圾回收远程分支引用）
- **get-url <简称>**：获取指定远程仓库的 URL 地址（配合 `--push` 仅显示推送地址）

**选项（通用）**

- **-v, --verbose**：显示详细信息
- **-h, --help**：显示帮助信息

> **注意**
>
> 1. `git remote -v` 是最常用的查看命令，会显示 fetch 和 push 两条 URL——默认情况下两者相同，但可设为不同（复杂工作流中，从 A 拉取、向 B 推送）
> 2. 一个本地仓库可以关联**多个**远程仓库（如同时关联 GitHub 和 Gitee），只需使用不同的简称
> 3. `git remote remove` 只是删除本地记录的远程关联信息，不会删除远程仓库本身的数据
> 4. 修改远程仓库地址时，使用 `git remote set-url` 而不是先删除再添加，可以避免丢失已配置的跟踪分支信息

**示例**

```bash
# 查看已关联的远程仓库
git remote
git remote -v

# 添加远程仓库关联
git remote add origin https://github.com/user/project.git

# 同时关联多个远程仓库
git remote add gitee https://gitee.com/user/project.git
git remote add github https://github.com/user/project.git

# 修改远程仓库地址（仓库迁移后常用）
git remote set-url origin https://github.com/user/new-project.git

# 重命名远程仓库
git remote rename origin upstream

# 查看远程仓库详细信息
git remote show origin

# 清理已删除的远程分支引用
git remote prune origin

# 删除远程仓库关联
git remote remove origin
```

# git fetch

用于从远程仓库**下载**最新的提交和分支信息到本地版本库，**但不会自动合并**到当前工作分支（最安全的同步方式）。

```bash
git fetch [选项] [远程仓库] [分支]
```

**关键理解**：`git fetch` = 下载远程数据到本地版本库，只更新远程跟踪分支（`origin/main`），不修改本地工作分支的文件。

```
fetch 前：
  本地 main ──A──B
  origin/main ──A──B
  远程 main ──A──B──C──D

执行 git fetch 后：
  本地 main ──A──B                 (不变)
  origin/main ──A──B──C──D         (更新)
  远程 main ──A──B──C──D
```

**选项**

- **无参数**：拉取默认远程仓库（通常是 `origin`）所有分支的最新提交
- **<远程仓库名>**：拉取指定远程仓库的所有分支
- **<远程仓库名> <分支名>**：只拉取指定远程仓库的指定分支
- **--all**：拉取所有已配置的远程仓库
- **-p, --prune**：拉取后同时清理本地已删除的远程分支引用（等价于 `git remote prune`）
- **--tags**：同时拉取所有标签（默认 fetch 不会自动拉取标签）
- **-t, --tags**：拉取所有标签（等同于 --tags）
- **-n, --no-tags**：抓取提交时不拉取任何标签（即使默认配置会拉取）
- **--depth <N>**：限制拉取的提交深度（配合浅克隆使用）
- **--unshallow**：将浅克隆仓库补全为完整历史
- **--dry-run**：模拟运行，显示会拉取哪些内容但不实际执行
- **-v, --verbose**：显示详细输出

> **注意**
>
> 1. `git fetch` 是**只读操作**，不会改变你的工作区文件、不会产生冲突，任何时候都可以安全执行
> 2. 执行 `git fetch` 后，本地仓库的远程跟踪分支（`origin/main`）会更新，但本地工作分支（`main`）不会自动跟进，需要手动执行 `git merge origin/main` 或 `git rebase origin/main`
> 3. 推荐在**查看远程更新但不准备合入本地**时使用 fetch（如先看看同事改了啥），也推荐在**多人协作、不确定当前本地修改是否会冲突**时用 fetch 代替 pull
> 4. `git fetch --prune` 可以自动清理已删除的远程分支引用，建议养成习惯定期执行

**示例**

```bash
# 拉取所有远程仓库的所有分支更新
git fetch

# 拉取指定远程仓库的所有分支
git fetch origin

# 只拉取指定远程仓库的指定分支
git fetch origin main

# 拉取所有远程仓库（如有多个 remote）
git fetch --all

# 拉取并清理已删除的远程分支引用
git fetch --prune

# 拉取包含标签
git fetch --tags

# 拉取后手动合并到本地分支（等价于 git pull 的效果）
git fetch origin
git merge origin/main

# 浅克隆后补全历史
git fetch --unshallow
```

# git pull

用于从远程仓库拉取更新并**自动合并**到当前本地分支（将 `git fetch` + `git merge` 合并为一步操作）。

```bash
git pull [选项] [远程仓库] [分支]
```

**关键理解**：`git pull` = `git fetch` + `git merge`（默认）。也可以配置为 `git fetch` + `git rebase`。

```
pull 前：
  本地 main ──A──B──X                (X = 本地新提交)
  origin/main ──A──B──C              (C = 远程新提交)

执行 git pull 后（默认 merge）：
  本地 main ──A──B──X──D             (D = 自动生成的合并提交)
                      └──C──┘

执行 git pull --rebase 后：
  本地 main ──A──B──C──X             (X 被重放在 C 之后，历史线性)
```

**选项**

- **--rebase**：拉取远程更新后，用 `git rebase` 代替 `git merge`（将本地提交重放在远程提交之上，保持线性历史，推荐协作时使用）
- **--no-rebase**：显式使用 `git merge`（即使配置了 pull.rebase 也会忽略）
- **--ff-only**：仅在能快进合并（fast-forward）时才执行合并，否则报错退出（安全合并）
- **--no-ff**：强制生成合并提交（即使可以快进合并）
- **--squash**：将远程更新压缩为一个合并提交（不保留远程分支的完整历史）
- **--autostash**：拉取前自动 `git stash` 暂存本地未提交的修改，拉取完成后自动恢复
- **-r, --rebase[=merges]**：使用 rebase 时保留合并提交的结构（`--rebase=merges`）
- **-v, --verbose**：显示详细输出
- **-q, --quiet**：安静模式，减少输出
- **-h, --help**：显示帮助信息

> **注意**
>
> 1. **"先拉再推"是协作的基本原则** —— 推送代码前，务必先 `git pull` 同步远程最新代码，避免推送被拒绝
> 2. `git pull` 和 `git fetch` 的区别：pull = 下载 + 合并（可能产生冲突），fetch = 仅下载（安全只读）。如果你不确定远程更新是否会影响本地工作，先用 `git fetch` 查看差异，再决定如何合并
> 3. **推荐场景下用 fetch 而不是 pull**：
>    - 当前工作区有未提交的修改，不确定是否与远程冲突时
>    - 想先审查远程的新提交内容再决定合并策略时
>    - 需要将远程更新合并到非当前分支时
> 4. `git pull --rebase` 是团队协作中强烈推荐的模式——它避免了多余的 "Merge branch" 合并提交，保持提交历史的线性清晰。可在全局配置设为默认：`git config --global pull.rebase true`
> 5. `git pull` 默认合并的是**远程跟踪分支到当前本地分支**，所以 `git pull origin main` 等价于：`git fetch origin main` + `git merge origin/main`
> 6. 如果 `git pull` 产生了冲突，Git 会暂停合并过程，等你解决冲突后 `git commit` 完成合并（或 `git merge --abort` 放弃合并）

**示例**

```bash
# 拉取远程 origin 的当前分支更新并合并
git pull

# 拉取指定远程仓库的指定分支
git pull origin main

# 使用 rebase 代替 merge（推荐）
git pull --rebase origin main

# 仅允许快进合并（如果无法快进就报错）
git pull --ff-only origin main

# 自动 stash 本地未提交修改后拉取
git pull --autostash

# 查看会拉取什么但不实际执行
git pull --dry-run
```

# git push

用于将本地仓库的提交**推送**到远程仓库。

```bash
git push [选项] [远程仓库] [分支名[:远程分支名]]
```

**选项**

- **无参数**：推送当前分支到已配置的上游分支（需先通过 `-u` 设置跟踪关系）
- **-u, --set-upstream <远程仓库> <分支>**：推送本地分支到远程分支，并建立跟踪关系——之后可以直接 `git push` 而不加参数
- **--force / -f**：强制推送，直接覆盖远程历史（**危险！**会丢失远程仓库上的提交）
- **--force-with-lease**：安全版强制推送——仅在远程没有新提交时强制覆盖（比 `--force` 安全得多）
- **--all**：推送所有本地分支到远程仓库（同名分支）
- **--tags**：推送所有本地标签到远程仓库
- **--delete <分支名>**：删除远程仓库上的指定分支
- **-d, --delete**：等同于 `--delete`
- **--dry-run**：模拟推送，显示会推送什么内容，但不实际执行
- **-n, --dry-run**：等同于 `--dry-run`
- **-v, --verbose**：显示详细输出
- **-q, --quiet**：安静模式
- **--set-upstream**：等同于 `-u`
- **--atomic**：原子推送——如果推送多个引用（分支或标签），只要有一个失败就全部回滚
- **--no-verify**：跳过远程仓库的 pre-receive 钩子检查
- **--prune**：删除远程仓库中本地已不存在的分支

> **注意**
>
> 1. **`--force` 极其危险**——它会无条件覆盖远程仓库的历史，如果你推送的远程分支上有别人提交的新代码，这些代码会**永久丢失**。只有在你**确定**需要覆盖远程历史（如修复敏感信息泄露）时才使用
> 2. **协作分支绝对不要 `--force`**——多人共同开发的特性分支或主分支，`--force` 会直接覆盖掉队友的提交，造成不可逆的损失
> 3. **`--force-with-lease` 是更安全的选择**——它会在推送前检查远程分支是否有本地未见过的新提交，如果有则拒绝推送，让你先用 `git fetch` 同步后再操作
> 4. **推送前先 `git pull`（或 `git pull --rebase`）**——如果远程有本地没有的提交，推送会被拒绝。此时应先拉取远程更新到本地，解决可能存在的冲突，再重新推送
> 5. **推送被拒绝时的处理步骤**：
>    （1）`git fetch origin` —— 先拉取远程更新
>    （2）`git log origin/main..HEAD` —— 查看本地有但远程没有的提交
>    （3）`git pull --rebase origin main` —— 将本地提交重放到远程提交之上
>    （4）若产生冲突，解决冲突后 `git add` + `git rebase --continue`
>    （5）`git push origin main` —— 推送成功
> 6. 首次推送一个分支到远程时必须使用 `-u` 建立跟踪关系，后续可以直接 `git push`
> 7. 推送到不同分支名使用 `<本地分支>:<远程分支>` 语法，如 `git push origin feature:main`

**示例**

```bash
# 首次推送并建立跟踪关系
git push -u origin main

# 后续推送（已建立跟踪关系后）
git push

# 推送指定分支到远程
git push origin feature-login

# 推送本地分支到远程的不同分支名
git push origin local-branch:remote-branch

# 安全版强制推送（推荐代替 --force）
git push --force-with-lease origin main

# 强制推送（危险！会覆盖远程历史）
git push --force origin main

# 推送所有本地分支
git push --all origin

# 推送所有标签
git push --tags

# 推送单个标签
git push origin v1.0.0

# 删除远程分支
git push origin --delete feature-old
# 或：git push origin -d feature-old

# 模拟推送（看会推送什么）
git push --dry-run origin main

# 原子推送（推送多个引用，部分失败则全回滚）
git push --atomic origin main v1.0.0
```

# 远程分支管理

## 跟踪分支（上游分支）概念

跟踪分支定义了**本地分支**与**远程分支**之间的关联关系。当本地分支设置了上游分支后：

- `git push`（无参数）会推送到上游分支
- `git pull`（无参数）会从上游分支拉取
- `git status` 会显示当前分支与上游分支的差异（领先 / 落后几个提交）

## 查看跟踪关系

```bash
# 显示所有本地分支及其跟踪的上游分支
git branch -vv

# 输出示例：
#   main       a1b2c3d [origin/main] 修复登录页面 bug
#   feature-x  e5f6g7h [origin/feature-x: ahead 2, behind 1] 新增搜索功能
#   dev        (无远程跟踪)
```

字段说明：
- `ahead 2`：本地分支比远程分支多 2 个提交（未推送）
- `behind 1`：本地分支比远程分支少 1 个提交（未拉取）

## 设置 / 修改跟踪关系

```bash
# 方式一：推送时建立跟踪关系（最常用）
git push -u origin feature-login

# 方式二：为已有分支设置上游
git branch -u origin/feature-login

# 方式三：为当前分支设置其他远程仓库的上游
git branch --set-upstream-to=gitee/main

# 方式四：创建新本地分支时直接跟踪远程分支
git checkout -b feature-login origin/feature-login
```

## 删除远程跟踪分支引用

```bash
# 方式一：清理所有已删除远程分支的跟踪引用
git remote prune origin

# 方式二：fetch 时自动清理
git fetch --prune

# 方式三：手动删除单个远程跟踪分支引用
git branch -d -r origin/feature-old
```

## 将远程分支检出到本地

```bash
# 方式一：创建新本地分支并跟踪远程分支（最常用）
git checkout -b 本地分支名 origin/远程分支名

# 方式二：直接检出远程分支（Git 自动创建同名本地分支并建立跟踪）
git checkout --track origin/feature-login
# 或简写：
git checkout feature-login   # 如果本地不存在但远程存在，Git 自动创建跟踪分支
```

# 冲突解决

## 冲突产生原因

当两个人修改了**同一文件的同一位置**，并且双方都提交了修改后，Git 无法自动判断应该保留谁的代码，就会产生冲突。

常见冲突场景：
- 两人的分支修改了同一行代码
- 一人删除了某段代码，另一人修改了同一段代码
- 多人同时修改了同一文件的末尾

## 识别冲突

```bash
# 查看哪些文件产生了冲突
git status

# 冲突文件会显示：
#   both modified:   src/index.js
#   both added:      src/new-file.js

# 查看冲突的具体内容
git diff
```

## 冲突标记说明

当 Git 无法自动合并时，会在冲突文件中插入冲突标记：

```
<<<<<<< HEAD
这是当前分支（HEAD）的代码
这是当前分支的第二行
=======
这是被合并分支（远程/特性分支）的代码
这是被合并分支的第二行
>>>>>>> feature-login
```

- `<<<<<<< HEAD` 到 `=======` 之间的内容：**当前分支**的代码
- `=======` 到 `>>>>>>> feature-login` 之间的内容：**被合并分支**的代码
- 需要手动选择保留哪部分，或者综合修改

## 解决流程

### 标准解决流程

```bash
# 1. 拉取远程更新时出现冲突
git pull origin main
# 输出：Auto-merging src/index.js
#       CONFLICT (content): Merge conflict in src/index.js
#       Automatic merge failed; fix conflicts and then commit the result.

# 2. 查看哪些文件冲突
git status

# 3. 编辑冲突文件，选择保留的内容（手动删除冲突标记）
#    例如保留两边的代码：直接把 <<<<<<<、=======、>>>>>>> 删掉，保留需要的代码

# 4. 标记冲突已解决
git add src/index.js

# 5. 完成合并提交
git commit
# Git 会自动生成合并提交信息，保存即可
```

### 放弃合并（回到合并前状态）

```bash
# 如果冲突太复杂，想先放弃本次合并
git merge --abort
```

### Rebase 时的冲突解决

```bash
# pull --rebase 或 git rebase 时产生冲突
git pull --rebase origin main

# 解决冲突步骤：
# 1. 编辑冲突文件，解决冲突
# 2. 标记已解决
git add src/index.js
# 3. 继续 rebase
git rebase --continue
# 4. 如果想跳过当前提交
git rebase --skip
# 5. 如果想放弃 rebase
git rebase --abort
```

## 使用工具辅助解决冲突

| 工具 | 特点 |
| :--- | :--- |
| **VS Code** | 内置冲突解决 UI，支持 "Accept Current" / "Accept Incoming" / "Accept Both" / "Compare Changes" |
| **IntelliJ IDEA** | 三路合并工具，左右显示两方代码，下方显示合并结果 |
| **Beyond Compare** | 专业文件比较工具，支持三路合并 |
| **Meld** | 免费开源的差异比较和合并工具 |

配置 VS Code 为合并工具：

```bash
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait $MERGED'
```

> **注意**
>
> 1. 产生冲突不是异常——**冲突是正常的协作现象**，只要有人和你修改了同一文件就有可能发生
> 2. 解决冲突时，**不要只保留自己的代码**，要和修改了同一段代码的同事沟通，确认正确的合并结果
> 3. 冲突文件中删除 `<<<<<<<`、`=======`、`>>>>>>>` 标记是必须的最后一步，否则 Git 认为冲突未解决
> 4. 养成频繁 `git pull` / `git fetch` 的习惯，减少单次合并涉及的范围，降低冲突复杂度
> 5. 团队协作中，合理拆分文件和模块、避免多人同时修改同一区域，可以从根本上减少冲突
