## 快速认识分支

分支是 Git 最强大的功能之一。通俗理解：

- 主分支（主流是`main`）：存放稳定的代码
- 功能分支（如`feature-login`）：开发新功能时，在独立分支操作，不影响主分支
- 修复分支（如`bugfix-123`）：修复 bug 时专用，修复后合并回主分支

> 核心价值：避免在主分支直接改代码，降低出错风险。

下面从技术角度深入理解分支的运作机制。

# 核心概念

## 分支的本质

分支的本质是一个**指向某个提交对象的可变指针**。当你创建新分支时，Git 实际上只是创建了一个新的指针，并让它指向当前所在的提交。每次提交后，当前分支指针会自动向前移动到最新的提交。

```
       feature
          ↓
    A---B---C
   /
-- D---E---F---G  main
                  ↑
                 HEAD
```

## HEAD 指针

HEAD 是一个特殊的指针，它**始终指向当前所在的分支**（而非直接指向提交）。当切换分支时，HEAD 会跟随移动到目标分支，Git 据此决定下一个父提交是谁。

## 分支工作流

在实际项目中，通常遵循以下分支命名规范和工作流：

- **main**：主分支，存放经过测试的稳定代码，不允许直接在 main 上开发
- **feature/***：功能分支（如 `feature/login`、`feature/payment`），从 main 拉出，开发完成后合并回 main
- **bugfix/***：修复分支（如 `bugfix/crash-on-empty`），从 main 拉出，修复 bug 后合并回 main
- **release/***：发布分支，从 main 拉出，用于版本发布前的最终测试和微调
- **hotfix/***：紧急修复分支，从 main 拉出，修复生产环境的严重问题，修复后同时合并到 main 和当前开发分支

> **核心理念**：分支隔离了不同方向的开发工作，让团队可以并行开发互不干扰。

# git branch

用于查看、创建、删除分支。

```bash
git branch [选项] [分支名]
```

**选项**

- 查看分支：
  - **无参数**：列出本地分支，`*` 标注当前所在分支，绿色高亮表示当前分支
  - **-v**：显示每个分支的最后一次提交信息（提交号 + 提交说明）
  - **-vv**：显示每个分支的上游跟踪分支以及领先/落后于上游的提交数
  - **-a**：列出所有分支，包含本地分支和远程跟踪分支
  - **-r**：仅列出远程跟踪分支（如 `origin/main`、`origin/feature/login`）
  - **--merged**：列出已合并到当前分支的所有分支（可用于确认哪些分支可以安全删除）
  - **--no-merged**：列出尚未合并到当前分支的分支（提醒这些分支还有未合并的修改）
  - **--sort=-committerdate**：按提交时间排序（`-` 前缀表示降序，`committerdate` 为提交日期）
- 创建 / 删除：
  - **分支名**：创建新分支（基于当前 HEAD 指向的提交），但**不自动切换**
  - **-d, --delete 分支名**：删除已合并到当前分支的分支（安全删除，未合并时会拒绝）
  - **-D**：强制删除分支，即使该分支上有未合并的修改
  - **-m, --move 新名称**：重命名当前分支（如果新名称已存在，则会覆盖，可使用 `-M` 强制移动）

> **注意**
>
> 1. 删除分支前，务必确认该分支上的修改已经合并到其他分支，否则会丢失未合并的提交
> 2. 不能删除当前所在的分支——需要先切换到其他分支再删除
> 3. 使用 `-m` 重命名分支后，如果该分支已有远程跟踪分支，需要手动更新远程引用
> 4. 远程分支的删除需要使用 `git push origin --delete 分支名`，本地 `git branch -d` 只能删除本地分支

# git checkout（分支切换）

用于切换分支、创建并切换分支，或恢复到工作区中指定文件的状态。

```bash
git checkout [选项] 分支名
```

**选项**

- **分支名**：切换到指定分支，HEAD 指向该分支，工作区文件同步更新为该分支的内容
- **-b 分支名**：创建新分支并立即切换过去（等价于先 `git branch 分支名` 再 `git checkout 分支名`）
- **-b 分支名 远程分支**：基于远程分支创建本地分支并切换过去，同时建立跟踪关系（例如 `git checkout -b feature/login origin/feature/login`）
- **-B 分支名**：强制创建新分支，如果分支已存在则重置到当前提交
- **-**：切换到上一个分支（类似 `cd -` 的用法，在两个分支间快速跳转）
- **--orphan 分支名**：创建一个无父提交的新分支，该分支将没有任何历史记录（常用于重构、创建全新的初始提交）

> **和 git switch 的关系**
>
> `git checkout` 是一个功能过于庞大的命令，它同时承担了「切换分支」「恢复文件」「分离头指针」等多个职责。从 Git 2.23 开始，官方将分支切换功能拆分为 `git switch`（专门切换分支）和 `git restore`（专门恢复文件），推荐在新版本中使用 `git switch` 进行分支操作，语义更加清晰。

> **注意**
>
> 1. 如果当前工作区有未提交的修改，且目标分支与当前分支在这些文件上存在差异，切换会被拒绝（需要先 commit 或 stash）
> 2. `git checkout -- 文件名` 的用法是恢复文件（不是切换分支），它会丢弃工作区对该文件的修改，**此操作不可撤销**
> 3. 切换到分离头指针状态（detached HEAD）时，所做的提交不会属于任何分支，切换回分支后可能丢失

# git switch

用于切换分支（Git 2.23+ 引入，功能从 `git checkout` 中拆分出来，语义更清晰，行为更安全）。

```bash
git switch [选项] [分支名]
```

**选项**

- **分支名**：切换到指定分支（等价于 `git checkout 分支名`）
- **-c, --create 分支名**：创建新分支并切换过去（等价于 `git checkout -b 分支名`）
- **-C, --force-create 分支名**：强制创建新分支，如果该分支名已存在则将其重置到当前 HEAD 并切换
- **-**：切换到上一个分支（与 `git checkout -` 行为一致）
- **--detach [提交号]**：切换到分离头指针状态，HEAD 直接指向某个提交而非分支（如果不指定提交号，则分离到当前 HEAD）
- **-t, --track 远程分支**：创建并切换到一个跟踪远程分支的本地分支，本地分支名自动取远程分支名的最后一段（例如 `git switch -t origin/feature/login` 会创建并切换到 `feature/login`）

> **注意**
>
> 1. `git switch` 比 `git checkout` 更安全——当工作区存在未提交的修改时，`git switch` 会严格拒绝可能导致冲突的切换，而 `git checkout` 有时会静默覆盖
> 2. `git switch` **不能**用于恢复工作区文件（恢复文件请使用 `git restore`），这种职责分离有助于避免误操作

# git merge

用于将其他分支的修改合并到当前分支。

```bash
git merge [选项] 分支名
```

**选项**

- **分支名**：将指定分支的修改合并到当前分支
- **--no-ff**：禁用 fast-forward 合并，无论是否能快进都生成一个新的合并提交节点，保留完整的分支脉络
- **--ff-only**：仅当可以 fast-forward 时才执行合并，否则拒绝并退出（用于确认没有额外分叉）
- **--squash**：将目标分支的所有修改压缩为一个整体的变更放入暂存区（不自动生成提交，需手动 `git commit`），不保留分支历史
- **--abort**：合并过程中遇到冲突时，放弃本次合并，恢复到合并前的状态
- **-m "msg"**：指定合并提交的提交信息（如果省略，Git 会自动生成如 `Merge branch 'feature' into main` 的默认信息）

**两种合并方式对比**

| 方式 | 特点 | 适用场景 |
| :--- | :--- | :--- |
| Fast-Forward | 不产生额外的合并提交，历史呈线性 | 个人开发分支、单一方向的小功能合并 |
| 三方合并 | 产生合并提交节点，保留分支分叉和合并脉络 | 多人协作、重要功能分支的合并 |

> **注意**
>
> 1. 合并前应确保当前分支的工作区是干净的（已 commit 或 stash），否则无法合并
> 2. 遇到合并冲突时不要慌张，Git 会在冲突文件中用 `<<<<<<<`、`=======`、`>>>>>>>` 标记冲突区域，手动编辑解决后执行 `git add` 并 `git commit` 即可
> 3. 使用 `--no-ff` 合并虽然会保留更完整的历史脉络，但也会让提交历史变得复杂，建议仅在合并重要功能分支时使用
> 4. 不要将大型功能分支直接合并到 main——推荐使用 Pull Request / Merge Request 来做代码审查后再合并

# git rebase

用于将当前分支的提交"移植"到目标分支的最新提交之后，使历史呈现为线性。

```bash
git rebase [选项] 目标分支
```

**选项**

- **目标分支**：将当前分支的提交变基到目标分支的最新提交之后
- **-i, --interactive**：进入交互式变基模式，可以合并（squash）、编辑（edit）、删除（drop）、重排（reorder）提交
- **--onto 新基分支 源分支**：将源分支从分叉点以来的提交变基到新基分支上（常用于将分支从一个基础转移到另一个基础）
- **--continue**：解决冲突后继续变基过程
- **--abort**：放弃本次变基，回到变基开始前的状态
- **--skip**：跳过当前导致冲突的提交（放弃该提交的所有修改，谨慎使用）

**流程示意图**

```
变基前：
      A---B---C feature
     /
--- D---E---F main

变基后（git rebase main）：
              A'---B'---C' feature
             /
--- D---E---F main
```

> 注意：变基后提交的 SHA 值会发生变化（用 A' 表示），因为提交的父提交和基础变了。

**rebase vs merge 对比**

| 维度 | merge | rebase |
| :--- | :---- | :----- |
| 历史结构 | 保留分支分叉和合并节点 | 线性历史，无分叉 |
| 提交记录 | 原始提交不变，SHA 不变 | 提交被重写，生成全新的 SHA |
| 适用场景 | 公共分支合并、多人协作 | 个人分支整理、提交历史美化 |
| 风险 | 低，不会改写历史 | 高，改写历史可能导致协作者混乱 |
| 冲突处理 | 只需解决一次 | 每个提交都可能产生冲突，需逐个解决 |

> **注意**
>
> 1. **黄金法则——永远不要对已推送到远程仓库的提交执行 rebase**。一旦远程分支的提交被 rewrite，其他协作者 pull 时会遇到大量冲突，严重影响团队协作
> 2. rebase 冲突可能需要逐个提交解决，如果涉及很多提交，推荐使用 `git merge` 代替
> 3. 在 rebase 过程中如果觉得太复杂，可以随时执行 `git rebase --abort` 放弃变基，恢复原状
> 4. rebase 适合在功能分支开发阶段定期同步 main 分支的最新代码，避免后期合并时出现大规模冲突
> 5. 交互式变基（`-i`）可以用于整理当前分支的提交历史，但同样只建议在推送到远程之前使用

# git cherry-pick

用于将指定的单个或多个提交"挑选"到当前分支，相当于将某个提交的变更内容在当前分支上重新应用一次。

```bash
git cherry-pick [选项] <提交号>...
```

**选项**

- **提交号**：指定一个或多个要挑选的提交（可连续多个，用空格分隔）
- **-n, --no-commit**：仅将修改应用到工作区和暂存区，不自动生成提交（可用于将多个 cherry-pick 合并为一个提交）
- **-e, --edit**：在应用修改后弹出编辑器编辑提交信息
- **-x**：在提交信息末尾追加一行 `(cherry picked from commit xxx)`，记录该提交的来源（常用于记录追溯）
- **--continue**：解决冲突后继续 cherry-pick
- **--abort**：放弃本次 cherry-pick，恢复到操作前的状态
- **--quit**：放弃本次 cherry-pick，但**不恢复**已应用的文件（保留已修改的文件内容）
- **-m, --mainline parent-number**：当挑选的提交是合并提交时，用此参数指定使用哪个父提交作为主线（值为 1 或 2，1 表示第一个父提交）

> **注意**
>
> 1. cherry-pick 本质上是"复制"提交的变更内容，而不是真正移动提交——新提交会有不同的 SHA 值
> 2. 挑选合并提交时必须使用 `-m` 参数指定主线编号，否则 Git 不知道应该采用哪个父分支的变更
> 3. cherry-pick 常用于从其他分支"捡"一个关键的 bug 修复到当前分支，而无需合并整个分支

# git stash

用于临时保存工作区和暂存区的修改，让工作区恢复到干净状态，以便执行其他操作（如切换分支、拉取代码等）。

```bash
git stash [选项] [信息]
```

**语法说明**

`git stash` 的默认行为等价于 `git stash push`——将当前所有已跟踪文件的修改（工作区 + 暂存区）保存到 stash 栈中，并恢复工作区到最近一次提交的状态。

**常用子命令**

- **push**：将当前修改存入 stash 栈（`git stash` 不带参数也是这个行为）
- **pop**：恢复最近一次 stash 的修改并**删除**该 stash 记录（等价于 `git stash apply && git stash drop`）
- **apply**：恢复最近一次 stash 的修改但**保留**记录（可用于将同一份 stash 应用到多个分支）
- **list**：列出所有 stash 记录，显示格式为 `stash@{N}: 说明信息`
- **show stash@{N}**：查看某次 stash 记录的详细变更内容（diff 格式）
- **drop stash@{N}**：删除指定的 stash 记录
- **clear**：清空整个 stash 栈中的所有记录（**不可恢复**，谨慎使用）

**选项（push 时使用）**

- **-m, --message "说明"**：为 stash 添加描述信息，便于在 `list` 中识别（例如 `git stash -m "WIP: 登录模块重构"`）
- **-u, --include-untracked**：同时暂存未跟踪的文件（新创建但未 `git add` 的文件）
- **-a, --all**：同时暂存未跟踪的文件和被 `.gitignore` 忽略的文件
- **-k, --keep-index**：暂存工作区的修改，但**保留**已 `git add` 到暂存区的内容在工作区中
- **-p, --patch**：交互式选择要暂存的内容，逐个文件确认是否要 stash（精细控制）

> **注意**
>
> 1. `git stash` 默认**不会**暂存未跟踪的文件——如果需要暂存新文件，必须使用 `-u` 或 `-a` 选项
> 2. 在不指定 stash 编号时，`pop` 和 `apply` 默认操作最近一次 stash 记录（即 `stash@{0}`），可以通过 `git stash pop stash@{2}` 指定具体记录
> 3. 在不同分支上应用 stash 可能会导致冲突，解决方式与普通的合并冲突相同
> 4. stash 栈是**本地存储**的，不会被 push 到远程仓库，请勿依赖 stash 来长期保存重要修改
> 5. 频繁 stash 而不清理会导致栈越来越长，建议定期 review 并清理不再需要的 stash 记录
