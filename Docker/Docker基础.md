# 何为Docker

**Docker 是一种轻量级的容器化技术**，它允许开发者将应用程序及其所有依赖（库、环境变量、配置文件等）打包成一个标准化单元（称为**容器**），从而实现**"一次构建，随处运行"**。

## 核心概念

| 概念                | 说明                                                         | 类比                   |
| :------------------ | :----------------------------------------------------------- | :--------------------- |
| **镜像(Image)**     | 只读模板，包含运行应用所需的代码、环境和配置（如一个`操作系统+软件`的快照） | 相当于"软件安装包"     |
| **容器(Container)** | 镜像的运行实例（一个轻量化的隔离进程）                       | 相当于"正在运行的软件" |
| **Dockerfile**      | 文本文件，定义如何构建镜像（包含一系列指令）                 | 相当于"菜谱"           |
| **仓库(Registry)**  | 存储和分发镜像的地方（如 Docker Hub）                        | 相当于"应用商店"       |

## 三大核心特性

1. **隔离性**
   - 每个容器拥有独立的文件系统、网络和进程空间
   - 通过 Linux 内核的 **cgroups** 和 **namespace** 实现资源隔离
2. **便携性**
   - 镜像可在任何支持 Docker 的系统中运行（Windows/macOS/Linux/云服务器）
   - 解决经典问题：*"在我电脑上能运行，为什么线上不行？"*
3. **轻量化**
   - 容器共享主机操作系统内核，无需虚拟化完整操作系统
   - 启动仅需**秒级**，资源占用远低于虚拟机

# 使用场景

## 开发与运维的“环境地狱”

假设你是一家电商公司的Java开发工程师小王，公司正在开发一个新的促销系统。让我们看看没有Docker时的开发流程：

### 周一早晨 - 开发环境搭建 

1. **安装依赖**：你需要安装JDK 8、Maven 3.6、MySQL 5.7和Redis 5.0
   - 花了3小时配置环境，期间遇到：
     - JDK版本冲突（系统已有JDK 11）
     - MySQL安装后无法启动（端口3306被占用）
     - Redis编译安装失败（缺少gcc）
2. **拉取代码**：从Git仓库获取项目后，运行 `mvn install` 报错：
   - "在本地能运行啊" - 同事老张说
   - 发现老张用的是Maven 3.8，而项目锁定在3.6

### 周三 - 测试环境部署 

当代码提交到测试环境后：

- 测试报告显示"支付功能异常"
- 排查发现：
  - 测试环境用的是MySQL 8.0（开发用5.7）
  - 某些SQL语法不兼容
  - Redis版本也不同导致缓存序列化问题

### 周五 - 生产环境上线 

运维团队部署时发现：

- 生产环境的CentOS 7与开发环境的Ubuntu 20.04行为不一致
- 内核参数差异导致线程池表现异常
- 最终导致上线延期2天

## Docker如何解决

开发团队在本地开发完成之后，编写dockerfile，通过docker的自动化部署来直接部署和开发一样的环境

~~~dockerfile
# 开发团队提供的Dockerfile
FROM openjdk:8-jdk
ENV MAVEN_VERSION=3.6.3

RUN apt-get update && \
    apt-get install -y maven=$MAVEN_VERSION && \
    mvn -v

COPY . /app
WORKDIR /app

EXPOSE 8080
CMD ["mvn", "spring-boot:run"]
~~~

### 效果对比

| 问题类型   | 传统方式           | Docker解决方案         |
| :--------- | :----------------- | :--------------------- |
| 环境一致性 | 每台机器环境不同   | 镜像保证环境完全一致   |
| 依赖冲突   | 需要手动解决       | 容器隔离，互不影响     |
| 多版本共存 | 难以实现           | 不同容器可运行不同版本 |
| 环境迁移   | 重新配置，耗时易错 | 一次构建，随处运行     |
| 资源隔离   | 进程相互影响       | 容器间完全隔离         |

# Docker优点

## 一、环境一致性解决方案

展示了软件开发中典型的"在我机器上能运行"的问题

Docker 通过以下核心技术彻底解决了软件开发中的环境一致性问题：

1. **标准化封装**
   - 将应用程序及其所有依赖（运行时、系统工具、库）打包成单一镜像
   - 镜像包含完整的运行环境，确保从开发到生产的一致性
2. **环境隔离**
   - 每个容器拥有独立的文件系统、网络和进程空间
   - 基于 Linux 内核的 cgroups 和 namespace 实现资源隔离
   - 避免应用间依赖冲突（如不同 Java/Python 版本共存）
3. **跨环境便携性**
   - 镜像可在任何支持 Docker 的平台运行（Windows/macOS/Linux/云）
   - 彻底消除"在我机器上能运行"的问题
4. **高效部署**
   - 容器启动时间：秒级（传统虚拟机需分钟级）
   - 停止/重启：毫秒级响应
   - 资源占用仅为传统虚拟机的 1/5-1/10

## 二、快速一致的交付流程

**CI/CD 工作流优化** 

| 阶段     | Docker 实现方式                 | 传统方式痛点             |
| :------- | :------------------------------ | :----------------------- |
| **开发** | 本地容器环境与团队共享          | 环境配置差异导致兼容问题 |
| **测试** | 使用相同镜像进行自动化/手动测试 | 测试环境与开发环境不一致 |
| **修复** | 在容器中直接调试并验证          | 难以复现生产环境问题     |
| **部署** | 镜像直接推送到生产环境          | 需重新配置环境，易出错   |

## 三、弹性扩展能力

**跨平台部署特性** 

- **支持环境**：
  - 开发者本地机器
  - 物理服务器/虚拟机
  - 公有云/私有云/混合云
  - 边缘计算设备
- **扩展模式**：
  - 垂直扩展：快速增加单个容器资源
  - 水平扩展：秒级启动多个容器实例
  - 自动扩缩容：根据负载动态调整容器数量

## 四、资源利用率提升

**与传统虚拟化对比**：

| 指标     | Docker 容器          | 传统虚拟机         | 优势幅度     |
| :------- | :------------------- | :----------------- | :----------- |
| 启动速度 | 1-3 秒               | 1-5 分钟           | 快 20-100 倍 |
| 磁盘占用 | 10MB-几百MB          | 10GB-几十GB        | 节省 90%+    |
| 内存开销 | 几乎为零（共享内核） | 每个 VM 需独立内存 | 节省 50-80%  |
| 并发密度 | 单机数百容器         | 单机10-20个VM      | 提升 5-10 倍 |

**适用场景：**

- 高密度部署（微服务架构）
- 资源受限的中小型部署
- 需要快速弹性伸缩的业务场景

# 镜像

Docker 镜像是 Docker 技术的核心组件之一，它是容器化应用的**静态模板**，包含了运行应用所需的完整环境和依赖

## 镜像的本质

1. **只读模板**

   - 镜像一旦创建便不可修改（immutable）
   - 所有变更通过创建新层实现

2. **分层存储结构**

   <img src=".\images\deepseek_mermaid_20250817_a1b12e.png" alt="deepseek_mermaid_20250817_a1b12e" style="zoom:25%;" />

   - 每层只存储与上一层的差异（节约空间）
   - 联合文件系统（如 overlay2）实现层叠加

3. **内容寻址存储**

   - 每个层由 SHA256 哈希唯一标识
   - 确保镜像内容完整性

## 镜像核心组成

| 组成部分     | 说明                             | 示例                                                 |
| :----------- | :------------------------------- | :--------------------------------------------------- |
| **基础镜像** | 底层操作系统或运行时环境         | `ubuntu:20.04`, `python:3.9`                         |
| **环境配置** | 系统变量、工作目录、暴露端口等   | `ENV PATH=/usr/bin`, `EXPOSE 8080`                   |
| **依赖文件** | 应用程序代码、库文件、配置文件等 | `COPY . /app`, `RUN pip install -r requirements.txt` |
| **启动命令** | 容器启动时执行的默认命令         | `CMD ["python", "app.py"]`                           |

# 镜像标签

## 什么是镜像标签

Docker 镜像标签（Tag）是用于标识和区分不同版本镜像的元数据，相当于给镜像起的"别名"。每个标签都指向一个具体的镜像ID（SHA256哈希值）。

## 标签的组成结构

```
[仓库地址/][命名空间/]镜像名:标签
```

**完整格式解析**

- **仓库地址**（可选）：默认是Docker Hub（`docker.io`），私有仓库如`registry.example.com` 
- **命名空间**（可选）：用户或组织名称，如 `library/`（官方镜像）
- **镜像名**（必需）：如`nginx`、`ubuntu`
- **标签**（可选）：默认 `latest`，如 `1.23.0`、`alpine` 

## 创建命令

```shell
docker image tag 源镜像[:标签] 新镜像名[:标签]
```

> **注意**
>
> 1. 标签操作不会创建新镜像，只是新增引用
> 2. 同一镜像ID可对应多个标签
> 3. 推送镜像前必须正确打标签

## 标签的核心特性

1. **多标签指向同一镜像**

   ```shell
   # 给已有镜像添加新标签
   docker tag nginx:1.23 my-nginx:latest
   ```

   - 不会创建新镜像，只是新增引用
   - 可通过 `docker image inspect` 查看所有关联标签

2. **标签版本控制**

   - 语义化版本：`v1.2.3` 
   - 构建时间：`20230815` 
   - 环境标识：`prod`/`test` 

3. **特殊标签规则**

   - `latest`：默认标签（不推荐生产环境使用）
   - `alpine`：基于Alpine Linux的轻量版本
   - `slim`：精简版本（移除非必要组件）

## 标签管理规范

### 命名建议

```shell
# 推荐格式
[项目名]-[版本号]-[环境]-[构建号]
示例：order-service-1.2.0-prod-b123
```

# 镜像管理

## 搜索镜像

用于从Docker Hub或其他镜像仓库搜索镜像

```shell
docker search [选项] 关键词
```

**选项** 

- **--limit**：限制返回结果数量（默认25）
- **--filter**：按条件过滤结果
- **--format**：自定义输出格式
- **--no-trunc**：显示完整的描述信息
- **--stars**：仅显示至少X星标的镜像（如`--stars=100`）
- **--is-official**：仅显示官方镜像
- **--is-automated**：仅显示自动构建的镜像

## 下载镜像

用于从镜像仓库拉取镜像到本地

```shell
docker pull [选项] 镜像名[:标签]
```

**选项**

- **-a, --all-tags**：下载仓库中所有标签的镜像
- **--platform**：指定平台（如 `linux/amd64`）
- **--quiet**：静默模式，仅输出镜像ID

> **注意**
>
> 1. 默认从Docker Hub拉取
> 2. 不指定标签时默认使用`:latest`
> 3. 私有仓库需先`docker login`
> 4. 下载进度条显示各层(layer)下载情况


## 镜像列表

查看本地镜像仓库内容

```shell
docker image ls [选项]
```

**选项**

- **显示控制**
  - **-a, --all**：显示所有镜像（包括中间层）
  - **-q, --quiet**：仅显示镜像ID
  - **--no-trunc**：显示完整的镜像ID（不截断）
- **信息筛选**
  - **--digests**：显示镜像摘要（Digest）
  - **--filter**：按条件过滤镜像（如`dangling=true`）
  - **--format**：使用Go模板自定义输出格式
- **排序与限制**
  - **--sort**：按指定字段排序（如`--sort=size`）
  - **--limit**：限制显示结果数量（Docker 23.0+）

**输出字段**

- REPOSITORY：镜像仓库名称（包含用户/组织名前缀）
- TAG：镜像标签（版本标识）
- IMAGE ID：镜像唯一标识（SHA256哈希的前12位）
- CREATED：镜像创建时间（相对时间或绝对时间）
- SIZE：镜像总大小（包含所有层）

**特殊状态说明**

- **`<none>`标记**：表示悬空镜像（Dangling images），通常是构建过程中的中间层或旧版本镜像
- **`missing`标记**：表示本地镜像的某些层已丢失（需重新拉取）

**注意**

> 1. `IMAGE ID`为SHA256的前12位
>2. 悬空镜像（`<none>`）可通过`docker image prune`清理
> 3. 使用`--no-trunc`显示完整ID


## 镜像信息

查看镜像详细信息


```shell
docker image inspect 镜像名/ID
```

**输出内容**

- 完整配置（环境变量、入口点等）
- 分层信息
- 创建时间
- 父镜像
- 容器配置


## 镜像创建信息

查看镜像构建历史记录

```shell
docker image history 镜像名/ID
```

**选项**

- **--no-trunc**：显示完整命令
- **-q, --quiet**：仅显示层ID
- **--human**：人性化显示大小


## 导出镜像

将镜像保存为tar归档文件

```shell
docker image save -o 文件名.tar 镜像名[:标签]
```

**选项**

- **-o, --output**：指定输出文件
- **--compress**：启用压缩

> **注意**
>
> 1. 导出包含镜像的所有层和元数据
> 2. 适合镜像迁移或备份
> 3. 文件较大，建议配合压缩使用


## 导入镜像

从tar文件加载镜像到本地仓库

```shell
docker image load -i 文件名.tar
```

**选项**

- **-i, --input**：指定输入文件
- **-q, --quiet**：静默模式

**与 `docker import` 区别** 

| 特性     | `load`                 | `import`              |
| :------- | :--------------------- | :-------------------- |
| 来源     | 由`save`导出的完整镜像 | 文件系统归档（如tar） |
| 保留历史 | 是                     | 否                    |
| 适用场景 | 镜像备份恢复           | 从rootfs创建基础镜像  |


## 删除镜像

移除本地镜像

```shell
docker rmi 镜像名/ID
# 或
docker image rm 镜像名/ID
```

**选项**

- **-f, --force**：强制删除（即使有容器使用该镜像）
- **--no-prune**：保留悬空的父镜像（不自动清理）
- **--filter**：按条件过滤要删除的镜像
- **-q, --quiet**：只显示被删除的镜像ID

> **注意**
>
> 1. 默认无法删除正在被容器使用的镜像（需先删除容器或使用`-f`）
> 2. 删除镜像会同时移除其所有关联的标签
> 3. 镜像分层存储中未被其他镜像引用的层会被自动清理
> 4. 重要数据应确保已通过卷(volume)持久化
> 5. 删除操作不可逆，建议先备份重要镜像

# 镜像制作

## 通过容器提交

可以直接将对应容器打包为镜像，使用 `docker commit` 命令来将容器制作成镜像

### docker commit

用于将容器的当前状态提交为新的镜像

```shell
docker commit [选项] 容器 [仓库名[:标签]]
```

**选项** 

- **-a, --author**：指定镜像作者信息（如 `-a "John Doe <john@example.com>"`）
- **-c, --change**：应用Dockerfile指令（支持`CMD`/`ENV`等）
- **-m, --message**：添加提交信息（类似Git commit message）
- **-p, --pause**：提交时暂停容器（默认为true）
- **--format**：指定输出格式（如`json`）
- **--quiet**：只显示新镜像ID

> **注意**
>
> 1. 提交的镜像会包含容器所有可写层的内容
> 2. 新镜像会继承原镜像的历史层
> 3. 敏感信息（如密码）可能被保留在镜像中
> 4. 不适合生产环境（建议使用Dockerfile构建）
> 5. 容器文件系统的临时文件也会被包含

### 制作过程

```shell
# 1. 运行基础容器
docker run -it --name temp ubuntu bash

# 2. 在容器内操作
apt update && apt install -y curl

# 3. 提交为新镜像
docker commit temp my-curl:1.0
```

commit是合并了save、load、export、import这几个特性的一个综合性的命令，它主要做了：

1. 将容器当前的读写层保存成一个新层。
2. 和镜像的历史层一起合并成一个新的镜像
3. 如果原本的镜像有3层，commit之后就会有4层，最新的一层为从镜像运行到commit之间对文件系统的修改。

**缺点**

- 无法版本控制
- 构建过程不透明
- 镜像臃肿

## dockerfile

### 核心步骤： 

```shell
# 1. 创建Dockerfile
FROM ubuntu:22.04
RUN apt-get update && apt-get install -y nginx
COPY index.html /var/www/html/
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

# 2. 执行构建
docker build -t my-nginx:1.0 .
```

### 关键指令说明

**操作指令** 

| 指令   | 说明                         |
| ------ | ---------------------------- |
| `RUN`  | 运行指定命令                 |
| `CMD`  | 启动容器时指定默认执行的命令 |
| `ADD`  | 添加内容到镜像               |
| `COPY` | 复制内容到镜像               |

**配置指令** 

| 指令          | 说明                               |
| ------------- | ---------------------------------- |
| `ARG`         | 定义创建镜像过程中使用的变量       |
| `FROM`        | 指定所创建镜像的基础镜像           |
| `LABEL`       | 为生成的镜像添加元数据标签信息     |
| `EXPOSE`      | 声明镜像内服务监听的端口           |
| `ENV`         | 指定环境变量                       |
| `ENTRYPOINT`  | 指定镜像的默认入口命令             |
| `VOLUME`      | 创建一个数据卷挂载点               |
| `USER`        | 指定运行容器时的用户名或UID        |
| `WORKDIR`     | 配置工作目录                       |
| `ONBUILD`     | 创建子镜像时指定自动执行的操作指令 |
| `STOPSIGNAL`  | 指定退出的信号值                   |
| `HEALTHCHECK` | 配置所启动容器如何进行健康检查     |
| `SHELL`       | 指定默认shell类型                  |

### 注意事项

#### FROM

**用途**：指定基础镜像
**用法**：`FROM <image>[:<tag>]`
>**注意**：
>
>- 必须是Dockerfile的第一个非注释指令
>- 尽量使用官方镜像和明确版本标签

#### RUN

**用途**：执行命令并创建新层
**用法**：

```dockerfile
RUN <command>  # shell格式
RUN ["executable", "param1", "param2"]  # exec格式
```

>**注意**：
>
>- 合并多个操作为单条RUN减少镜像层
>- 记得清理临时文件

#### CMD

**用途**：设置容器默认执行的命令
**用法**：

```dockerfile
CMD ["executable","param1","param2"]  # 推荐格式
CMD command param1 param2
```

> **注意**：
> 
> - 每个Dockerfile只能有一条有效CMD
> - 会被`docker run`后面的命令覆盖

#### COPY

**用途**：复制本地文件到镜像
**用法**：`COPY <src> <dest>`
>**注意**：
>
>- 源路径是相对于构建上下文的
>- 不会自动解压文件

#### ADD

**用途**：增强版COPY（支持URL和解压）
**用法**：`ADD <src> <dest>`
>**注意**：
>
>- 仅当需要自动解压或远程下载时使用
>- 可能造成非预期行为，优先用COPY

#### ENTRYPOINT

**用途**：设置容器的主程序
**用法**：

```dockerfile
ENTRYPOINT ["executable", "param1"]
ENTRYPOINT command param1
```

>**注意**：
>
>- 与CMD配合使用（CMD作为参数）
>- 不容易被运行时命令覆盖

#### EXPOSE

**用途**：声明容器监听的端口
**用法**：`EXPOSE <port>`
>**注意**：
>
>- 只是文档说明，实际端口映射需用`-p`参数
>- 可以指定协议（如`80/tcp`）

#### ENV

**用途**：设置环境变量
**用法**：`ENV <key>=<value>`
>**注意**：
>
>- 会持久化到容器运行时
>- 敏感数据应使用ARG或secrets

#### ARG

**用途**：定义构建时的变量
**用法**：`ARG <name>[=<default>]`
>**注意**：
>
>- 只在构建期间有效
>- 通过`--build-arg`覆盖默认值

#### VOLUME

**用途**：创建数据卷挂载点
**用法**：`VOLUME ["/data"]`
>**注意**：
>
>- 避免容器层写入大量数据
>- 实际挂载需用`-v`参数

#### WORKDIR

**用途**：设置工作目录
**用法**：`WORKDIR /path`
>**注意**：
>
>- 对后续指令生效
>- 使用绝对路径

#### USER

**用途**：指定运行用户
**用法**：`USER <user>[:<group>]`
>**注意**：
>
>- 应先创建相应用户
>- 避免使用root

#### HEALTHCHECK

**用途**：定义健康检查
**用法**：

```dockerfile
HEALTHCHECK --interval=5m --timeout=3s \
  CMD curl -f http://localhost/ || exit 1
```

>**注意**：
>
>- 检查失败会标记容器为unhealthy
>- 可覆盖默认检查参数

#### ONBUILD

**用途**：设置延迟执行的指令
**用法**：`ONBUILD <INSTRUCTION>`
>**注意**：
>
>- 只在被下游镜像构建时触发
>- 适用于基础镜像制作

# 容器

## 容器的结构

1. **运行时架构

   ```
   ┌───────────────────────┐
   │     Container RW      │  # 容器可写层（日志/临时文件等）
   ├───────────────────────┤
   │     Image Layers      │  # 共享镜像的只读层
   └───────────────────────┘
   ```

2. **核心组件**

   - 可写层（容器层）：存储运行时产生的所有修改
   - 挂载点（Volume）：持久化数据存储区域
   - 命名空间（Namespace）：隔离的进程/网络视图
   - 控制组（Cgroup）：资源限制单元

## 容器和镜像对比

| 特性         | 镜像(Image)            | 容器(Container)           |
| :----------- | :--------------------- | :------------------------ |
| **本质**     | 只读的模板文件包       | 镜像的运行实例            |
| **状态**     | 静态不可变             | 动态可读写                |
| **存储**     | 分层存储（Layer）      | 容器层（可写层）          |
| **生命周期** | 长期存在               | 临时性（可随时创建/删除） |
| **数量关系** | 一个镜像可生成多个容器 | 容器必须基于某个镜像      |

## 容器和镜像的关系

1. **创建过程**

   ![deepseek_mermaid_20250817_4257de](.\images\deepseek_mermaid_20250817_4257de.png)

2. **存储关系**

   - 镜像层：所有容器共享的只读部分

   - 容器层：每个容器独有的可写层

   - 典型磁盘使用：

     ```shell
     $ docker system df
     TYPE        TOTAL     ACTIVE    SIZE      RECLAIMABLE
     Images      3         2         1.2GB     500MB
     Containers  2         1         25MB      25MB
     ```

3. **生命周期交互**

   - 删除镜像需先删除依赖容器
   - 容器修改可通过`docker commit`生成新镜像
   - 镜像更新需重建容器才能生效

# 容器管理

## 创建容器

用于创建一个新的容器但不自动启动它

~~~shell
docker create [选项] 镜像 [命令] [参数...]
~~~

**选项**

- **基础选项**
  - **-d, --detach**：后台运行容器
  - **--name**：为容器指定名称
  - **-it**：交互模式运行（通常组合使用：`-i`保持STDIN打开，`-t`分配伪终端）
  - **--rm**：容器退出时自动删除
- **资源限制**
  - **-m, --memory**：内存限制（如：`-m 512m`）
  - **--memory-swap**：内存+交换分区限制
  - **--cpus**：CPU核心数限制（如：`--cpus=1.5`）
  - **--cpu-shares**：CPU权重（默认1024）
- **网络配置**
  - **-p, --publish**：端口映射（格式：`主机端口:容器端口`）
  - **-P, --publish-all**：发布所有暴露的端口
  - **--network**：指定网络（如：`--network=bridge`）
  - **--hostname**：设置容器主机名
- **存储卷**
  - **-v, --volume**：挂载卷（格式：`主机路径:容器路径[:选项]`）
  - **--mount**：更详细的挂载方式
  - **--tmpfs**：挂载临时文件系统
- **环境变量**
  - **-e, --env**：设置环境变量（如：`-e MYSQL_ROOT_PASSWORD=123456`）
  - **--env-file**：从文件读取环境变量
- **安全选项**
  - **--cap-add**：添加Linux能力
  - **--cap-drop**：删除Linux能力
  - **--read-only**：以只读模式运行容器
  - **--security-opt**：安全选项

> **注意**
>
> 1. 与`docker run`不同，`create`只创建容器不自动启动
> 2. 容器状态会显示为"Created"（可通过`docker ps -a`查看）
> 3. 创建后需使用`docker start`启动容器
> 4. 适合需要精细控制容器启动流程的场景
> 5. 所有设置选项与`docker run`命令基本一致

## 重启容器

用于重启一个或多个正在运行的容器

```shell
docker restart [选项] 容器 [容器...]
```

**选项**

- **-t, --time**：设置停止超时时间（单位：秒，默认10秒）
- **--signal**：发送自定义信号给容器（默认SIGTERM）
- **-h, --help**：显示帮助信息

> **注意**
>
> 1. 会先停止容器再重新启动（不是热重启）
> 2. 容器将使用最初创建时的相同配置重新启动
> 3. 对已停止的容器执行会直接启动它
> 4. 重启期间服务会有短暂中断
> 5. 适用于配置更新后需要重新加载的场景
> 6. 与`docker stop`+`docker start`组合效果相同，但更原子化

## 停止容器

用于停止一个或多个运行中的容器

```shell
docker stop [选项] 容器 [容器...]
```

**选项**

- **-t, --time**：设置停止超时时间（单位：秒，默认10秒）
- **--signal**：发送自定义信号给容器（默认SIGTERM）
- **-h, --help**：显示帮助信息

> **注意**
>
> 1. 默认会先发送SIGTERM信号，超时后发送SIGKILL强制终止
> 2. 停止的容器可以通过`docker start`重新启动
> 3. 容器停止后会保留所有文件系统和配置
> 4. 使用`-t/--time`可以调整优雅停止的等待时间
> 5. 对已停止的容器执行不会产生任何效果
> 6. 与`docker kill`相比更优雅（允许进程完成清理工作）

## 列出容器

用于列出容器

```shell
docker ps [选项]
```

**选项**

- **-a, --all**：显示所有容器（默认只显示运行中的）
- **-f, --filter**：根据条件过滤输出
  - `status=running|created|restarting|paused|exited|dead`
  - `name=容器名称`
  - `id=容器ID`
  - `label=key`或`label=key=value`
  - `ancestor=镜像名`（使用指定镜像创建的容器）
  - `before`/`since=容器`（时间/容器关系）
- **--format**：使用Go模板格式化输出
- **-n, --last**：显示最后创建的n个容器（包括所有状态）
- **-l, --latest**：显示最新创建的容器（包括所有状态）
- **--no-trunc**：不截断输出
- **-q, --quiet**：只显示容器ID
- **-s, --size**：显示容器大小（文件系统）
- **--since**：显示在指定容器/时间之后创建的容器
- **--until**：显示在指定容器/时间之前创建的容器
- **-h, --help**：显示帮助信息

**输出字段说明**

| 字段         | 说明                           |
| :----------- | :----------------------------- |
| CONTAINER ID | 容器唯一标识（SHA256的前12位） |
| IMAGE        | 创建容器使用的镜像             |
| COMMAND      | 容器启动时运行的命令           |
| CREATED      | 容器创建时间                   |
| STATUS       | 运行状态（Up/Exited/Paused等） |
| PORTS        | 端口映射情况                   |
| NAMES        | 容器名称                       |

> **注意**
>
> 1. 默认输出包含：容器ID、镜像、命令、创建时间、状态、端口、名称
> 2. 停止的容器会显示退出状态码（非0通常表示错误）
> 3. 使用`--format`可以完全自定义输出格式
> 4. 过滤条件可以组合使用，如`-f "name=web" -f "status=running"`
> 5. 在生产环境中建议配合`-q`选项用于脚本处理

## 运行容器

用于创建并立即启动一个新的容器

```shell
docker run [选项] 镜像 [命令] [参数...]
```

**选项** 

- **运行模式**
  - **-d, --detach**：后台运行容器
  - **-it**：交互模式运行（组合使用：`-i`保持STDIN打开，`-t`分配伪终端）
  - **--rm**：容器退出时自动删除

- **容器配置**
  - **--name**：为容器指定名称
  - **--hostname**：设置容器主机名
  - **--restart**：设置重启策略（no, on-failure, always, unless-stopped）
  - **--workdir**：设置容器内工作目录

- **资源限制**
  - **-m, --memory**：内存限制（如：`-m 512m`）
  - **--memory-swap**：内存+交换分区限制
  - **--cpus**：CPU核心数限制（如：`--cpus=1.5`）
  - **--cpu-shares**：CPU权重（默认1024）

- **网络配置**
  - **-p, --publish**：端口映射（格式：`主机端口:容器端口`）
  - **-P, --publish-all**：发布所有暴露的端口
  - **--network**：指定网络模式
  - **--add-host**：添加主机到IP映射（格式：`host:ip`）
  - **--dns**：设置自定义DNS服务器

- **存储卷**
  - **-v, --volume**：挂载卷（格式：`主机路径:容器路径[:选项]`）
  - **--mount**：更详细的挂载方式
  - **--tmpfs**：挂载临时文件系统

- **环境变量**
  - **-e, --env**：设置环境变量
  - **--env-file**：从文件读取环境变量

- **安全选项**
  - **--cap-add**：添加Linux能力
  - **--cap-drop**：删除Linux能力
  - **--security-opt**：安全选项
  - **--read-only**：以只读模式运行容器


> **注意**
>
> 1. 这是最常用的容器操作命令
> 2. 如果本地不存在指定镜像，会自动从仓库拉取
> 3. 默认在前台运行（除非使用`-d`选项）
> 4. 容器停止后默认会保留（除非使用`--rm`选项）
> 5. 使用`-it`可进入交互式shell
> 6. 端口映射必须使用`-p`参数显式声明
> 7. 数据卷挂载需要使用绝对路径

## 挂起/恢复容器

用于暂停/恢复容器中所有进程的执行

```shell
docker pause 容器 [容器...]
docker unpause 容器 [容器...]
```

**选项** 

- **无特殊选项**：这两个命令通常不需要额外选项

**相关命令对比** 

| 命令    | 效果     | 资源占用 | 恢复速度     |
| :------ | :------- | :------- | :----------- |
| `pause` | 冻结进程 | 保持占用 | 即时恢复     |
| `stop`  | 终止进程 | 释放资源 | 需要重新启动 |
| `kill`  | 强制终止 | 完全释放 | 需要重新启动 |

> **注意**
>
> 1. `pause`会冻结容器内的所有进程（使用cgroups freezer功能）
> 2. 暂停的容器仍会占用系统资源（内存等），只是进程被挂起
> 3. 暂停状态可通过`docker ps`查看（显示为Paused）
> 4. 网络连接在暂停期间会保持但无响应
> 5. 与`docker stop`不同，暂停可以快速恢复且不终止进程
> 6. 适用于临时冻结容器状态而不想停止容器的场景

## 进入容器

用于在运行中的容器内执行命令

```shell
docker exec [选项] 容器 命令 [参数...]
```

**选项**

- **基础选项 ** 
    - **-d, --detach**：后台运行命令
    - **-e, --env**：设置环境变量
    - **-i, --interactive**：保持STDIN打开（即使未连接）
    - **-t, --tty**：分配伪终端（通常与-i一起使用）
    - **-u, --user**：指定执行用户（格式：用户名或UID）
- **工作目录 ** 
    - **-w, --workdir**：设置命令的工作目录
- **其他选项** 
    - **--env-file**：从文件读取环境变量
    - **--privileged**：赋予扩展权限
    - **--index**：对多个实例容器指定索引（默认1）

> **注意**
>
> 1. 容器必须处于运行状态（Running）才能使用exec
> 2. 使用`-it`组合可进入交互式会话（类似SSH）
> 3. 执行的命令会继承容器的环境变量
> 4. 退出交互会话不会停止容器（与`docker attach`不同）
> 5. 适合调试、维护或执行一次性任务
> 6. 对容器文件系统的修改会持久化

## 删除容器

用于删除一个或多个容器

```shell
docker rm [选项] 容器 [容器...]
```

**选项**

- **-f, --force**：强制删除运行中的容器（默认只能删除停止的容器）
- **-v, --volumes**：同时删除关联的匿名卷
- **-l, --link**：删除指定的容器链接（已废弃）
- **--filter**：根据条件过滤要删除的容器
- **-q, --quiet**：只显示容器ID（用于脚本处理）

> 4. 命名卷（named volume）默认不会被删除（除非显式使用`docker volume rm`）
> 5. 重要数据应提前备份

# 数据管理

## 存储

默认情况下，容器内创建的所有文件都存储在**可写的容器层**上。这个层依赖于容器本身的生命周期，存在几个致命缺点：

1. **数据易失**：容器被删除时，其容器层和其中的所有数据也会被一并销毁。
2. **难以导出**：数据“困”在容器内部，其他进程或主机难以直接访问。
3. **性能低下**：容器层通过存储驱动与主机交互，其读写性能低于直接访问主机文件系统。

因此，为了保存重要数据（如数据库文件、应用程序日志、配置文件）或在容器与主机、容器与容器之间共享数据，我们必须使用 Docker 提供的**挂载（Mount）** 机制将数据存储在容器之外。

##  挂载

挂载的本质是将一个外部数据源（如主机目录、Docker 管理的卷）关联到容器内部的一个路径上。容器内的应用程序像访问普通目录一样访问这个路径，但实际上所有的读写操作都发生在外部数据源上。

Docker 主要支持四种挂载类型，适用于不同场景：

| 挂载类型      | 说明                                                         | 使用场景                         | 特点                                                   |
| :------------ | :----------------------------------------------------------- | :------------------------------- | :----------------------------------------------------- |
| Volume Mounts | Docker管理的持久化数据卷，存储在/var/lib/docker/volumes/目录下 | 数据库存储、应用数据持久化       | 独立于容器生命周期、可在容器间共享、支持数据备份和迁移 |
| Bind Mounts   | 将宿主机目录或文件直接挂载到容器内                           | 开发环境代码热更新、配置文件挂载 | 方便直接操作文件、依赖宿主机文件系统、适合开发调试     |
| Tmpfs Mounts  | 将数据临时存储在宿主机内存中                                 | 敏感数据存储、临时文件存储       | 高性能、数据易失性、增加内存占用                       |
| Named Pipes   | 在容器间建立命名管道进行通信                                 | 容器间进程通信、数据流传输       | 低延迟、进程间通信、适合流式数据传输                   |

### Volume mounts（卷挂载）

Volume 是 Docker 完全管理的持久化数据存储机制，是生产环境中数据管理的**最佳实践** 

#### 常用操作 

~~~shell
# 创建一个新的数据卷（Docker 会自动生成名称）
docker volume create my-app-data

# 列出所有数据卷
docker volume ls

# 查看某个数据卷的详细信息（包括其在主机上的实际存储路径）
docker volume inspect my-app-data

# 删除一个未使用的数据卷
docker volume rm my-app-data

# 清理所有未被任何容器引用的数据卷（谨慎操作！）
docker volume prune
~~~

#### 使用卷启动容器

有两种语法可以实现挂载，`--mount` 语法更明确，而 `-v` 语法更简洁

**语法一：`--mount` (推荐，语法更清晰)**

~~~shell
docker run -d \
  --name my-nginx \
  --mount type=volume,source=my-nginx-volume,target=/usr/share/nginx/html \
  nginx:latest
~~~

- **`--mount` 更多参数** 

  | 参数             | 说明                                                    | 使用示例                 | 最佳实践                           |
  | :--------------- | :------------------------------------------------------ | :----------------------- | :--------------------------------- |
  | `source, src`    | 指定要挂载的卷名，如果卷不存在，Docker 会自动创建它     | `src=myvolume`           | 使用有意义的名称便于识别和管理     |
  | `target, dst`    | 指定卷在容器内的挂载路径                                | `dst=/data/app`          | 遵循容器内标准目录结构             |
  | `type`           | 指定挂载类型，可选值：volume、bind、tmpfs，默认为volume | `type=volume`            | 根据数据持久化需求选择合适类型     |
  | `readonly, ro`   | 只读挂载标志，设置后容器内无法修改挂载内容              | `ro=true`                | 对配置文件等静态内容建议只读挂载   |
  | `volume-subpath` | 卷的子路径，只挂载数据卷中的指定子目录                  | `volume-subpath=/config` | 用于精确控制挂载范围，提高安全性   |
  | `volume-opt`     | 卷的额外选项，用于指定卷的特定行为                      | `volume-opt=size=10G`    | 根据实际需求配置，避免过度使用     |
  | `volume-nocopy`  | 创建卷时不从容器复制数据                                | `volume-nocopy=true`     | 用于避免不必要的数据复制，提高性能 |

**语法二：`-v` 或 `--volume` (更简洁)** 

```shell
docker run -d \
  --name my-nginx \
  -v my-nginx-volume:/usr/share/nginx/html \
  nginx:latest
```

- **格式：`-v <卷名>:<容器内路径>`**

> **`-v` 参数如何判断类型？** 
>
> Docker 会根据 `-v` 参数中冒号 (`:`) **左侧的格式**自动判断类型：
>
> - **如果左侧是绝对路径**（如 `/home/user/data` 或 `C:\data`），则创建 **Bind Mount**。
> - **如果左侧是简单名称**（没有斜杠 `/`，如 `my_volume`），则创建或使用 **Named Volume**。
> - **如果只提供了右侧**（如 `/data`），则创建 **Anonymous Volume**（匿名卷）。

### Bind mounts（绑定挂载）

Bind Mount 允许你将主机上的一个**特定目录或文件**直接挂载到容器内部。这是一种强大且灵活的方式，但将容器与主机的文件系统结构紧密耦合。

#### 常用操作

由于 Bind Mount 直接使用主机上的现有路径，因此不需要像 Volume 那样的专用管理命令（`create`, `ls`, `inspect`, `rm`）。你只需要使用标准的 shell 命令来管理主机上的目录和文件即可

```shell
# 在主机上创建用于绑定挂载的目录
mkdir -p /home/user/my-app-data

# 在主机上创建或编辑配置文件
vim /home/user/my-app-config.conf
```

#### 使用绑定挂载启动容器

与 Volume 一样，也有两种语法可以实现挂载。

**语法一：`--mount` (推荐，语法更清晰)**

```shell
docker run -d \
  --name my-dev-server \
  --mount type=bind,source=/home/user/project,target=/app/code \
  nginx:latest
```

- **`--mount` 更多参数 (Bind Mount 特定)**

| 参数               | 说明                                                         | 使用示例                    | 最佳实践                                                     |
| :----------------- | :----------------------------------------------------------- | :-------------------------- | :----------------------------------------------------------- |
| `type`             | **必须明确指定为 `type=bind`**                               | `type=bind`                 | 明确指示使用绑定挂载类型                                     |
| `source, src`      | **主机上的绝对路径**。如果路径不存在，Docker 会**自动创建为目录**。 | `src=/home/user/data`       | 使用绝对路径，避免歧义。确保 Docker 引擎有该路径的读取（和写入）权限。 |
| `target, dst`      | 容器内的挂载路径。                                           | `dst=/app/data`             | 遵循容器内标准目录结构。如果目标路径非空，其原有内容会被挂载内容覆盖。 |
| `readonly, ro`     | 只读挂载标志。设置后，容器内无法修改挂载目录下的内容。       | `ro=true`                   | 对配置文件等只读资源强烈建议启用，增强安全性。               |
| `bind-propagation` | 设置挂载的传播属性（`rprivate`, `private`, `rshared`, `shared`, `rslaved`, `slaved`）。控制挂载点事件如何传播。 | `bind-propagation=rprivate` | 大多数情况下使用默认值 `rprivate` 即可，除非有特殊的嵌套挂载需求。高级功能。 |

**语法二：`-v` 或 `--volume` (更简洁)**

```shell
docker run -d \
  --name my-dev-server \
  -v /home/user/project:/app/code \
  nginx:latest
```

- 格式：**`-v <主机绝对路径>:<容器内路径>`**

> **注意**：
>
> - **`-v` 参数如何判断类型？** 
>
>   Docker 会根据 `-v` 参数中冒号 (`:`) **左侧的格式**自动判断类型：
>
>   - **如果左侧是绝对路径**（如 `/home/user/data` 或 `C:\data`），则创建 **Bind Mount** 
>   - **如果左侧是简单名称**（没有斜杠 `/`，如 `my_volume`），则创建或使用 **Named Volume** 
>   - **如果只提供了右侧**（如 `/data`），则创建 **Anonymous Volume**（匿名卷）
>
> - **挂载发生后，容器内目标目录的原始内容会被完全隐藏、无法访问，并被源目录（主机目录或卷）的内容彻底替换和覆盖。**
>
> -  原始内容**未被删除**，仍存在于只读镜像层中，只是被挂载点“屏蔽”了。

| -------------- | ------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |

# 资源管理

## 资源隔离

### 问题引入

如果一个宿主机内运行了多个容器，会带来以下问题：

1. **文件混乱**：大家共用同一个文件系统，可能会误删或覆盖彼此的文件。
2. **进程冲突**：所有容器中的进程都来自同一个“父进程”，互相能看到甚至干扰对方。
3. **网络冲突**：多个容器可能抢用同一个IP或端口，导致服务不可用。
4. **主机名冲突**：如果多个容器使用相同的主机名，会造成识别混乱。
5. **用户权限混乱**：不同容器中的用户（比如都是root）可能越权操作，带来安全隐患。

### 解决方案

Linux 内核提供了一种叫做 **Namespace** 的机制，可以为不同进程划分出独立的运行环境，就像给每个容器分配了一个“小单间”，彼此互不干扰

Namespace在内核层实现，即有一些不同类型的命名空间都部署在核内，各个容器运行在同一个docker主进程并且共用同一个宿主机系统内核，各个docker容器运行在宿主机的用户空间，每个容器都要有类似于虚拟机一样的相互隔离的运行空间，但是容器技术是在一个进程内实现运行指定服务的运行环境，并且还可以保护宿主机内核不受其他进程的干扰和影响，如文件系统、网络空间、进程空间等

Docker 正是利用这一机制，让多个容器可以共用同一个操作系统内核，但又各自拥有独立的运行空间

| 隔离类型              | 功能说明                                                   | 系统调用参数    | 内核版本 | 应用场景举例                               |
| :-------------------- | :--------------------------------------------------------- | :-------------- | :------- | :----------------------------------------- |
| **Mount Namespace**   | 隔离文件系统，使每个容器拥有独立的目录结构和挂载点         | `CLONE_NEWNS`   | 2.4.19   | 每个容器有自己的系统文件，互不影响         |
| **IPC Namespace**     | 隔离进程间通信（如消息队列、共享内存），避免容器间通信干扰 | `CLONE_NEWIPC`  | 2.6.19   | 容器内部通信，不影响其他容器               |
| **UTS Namespace**     | 隔离主机名和域名，每个容器可以有自己的主机名               | `CLONE_NEWUTS`  | 2.6.19   | 容器可以自定义主机名，便于识别和管理       |
| **PID Namespace**     | 隔离进程ID，每个容器内的进程都认为自己是“第一个进程”       | `CLONE_NEWPID`  | 2.6.24   | 容器内进程独立，看不到宿主或其他容器的进程 |
| **Network Namespace** | 隔离网络设备、IP地址、端口等，每个容器有独立的网络栈       | `CLONE_NEWNET`  | 2.6.29   | 容器可以有自己的IP和端口，不会冲突         |
| **User Namespace**    | 隔离用户和用户组ID，增强安全性，防止容器内用户越权操作     | `CLONE_NEWUSER` | 3.8      | 容器内可以有root用户，但权限被限制在容器内 |

**简单理解** 

可以把 Namespace 想象成一个个“隔离舱”，每个容器住在一个隔离舱里：

- 有自己的文件柜（Mount）
- 有自己的内部电话（IPC）
- 有自己的门牌号（UTS）
- 有自己的员工编号（PID）
- 有自己的网络线路（Network）
- 有自己的钥匙和权限（User）

这样，即使很多容器运行在同一台机器上，也不会互相干扰，就像一个个独立的小系统。

### MNT Namespace

提供磁盘挂载点和文件系统的隔离能力，使容器拥有独立的文件系统层次结构。

**那么宿主机的PID与容器内的PID是什么关系？**

1. 独立的 PID 命名空间

   - 每个 Docker 容器都有自己独立的 PID 命名空间。
   - 容器内的进程 PID 从 1 开始编号,与宿主机上的 PID 是相互独立的。
   
2. PID 映射

   - 容器内的进程 PID 与宿主机上的进程 PID 之间是有映射关系的。
   - 通过 `docker inspect <container_id>` 命令,可以查看容器内进程的 PID 与宿主机上进程 PID 的对应关系。
   
3. PID 可见性

   - 容器内的进程只能看到容器内部的 PID。
   - 宿主机上的进程可以看到容器内部的 PID,但容器内的进程无法看到宿主机上的 PID。
   
4. PID 隔离

   - 容器内的进程无法访问或影响宿主机上的其他进程。
- 宿主机上的进程可以访问和管理容器内的进程。

## 资源限制

### Cgroup介绍

在一个容器内部，如果不对其做任何资源限制，则宿主机会允许其占用无限大的内存空间，有时候会因为代码bug程序会一直申请内存，直到把宿主机内存占完为了避免此类的问题出现，宿主机有必要对容器进行资源分配限制，比如cpu、内存等

Linux Cgroups的全称是Linux control Groups，它最重要的作用就是限制一个进程组能够使用的资源上线，包括cpu、内存、磁盘、网络等等

### 容器CPU限制

#### 相关参数

| --cpu-period  | 100000 | 设置CPU CFS调度周期(单位:微秒)。必须与--cpu-quota一起使用。  | • 不建议单独使用 • 建议使用--cpus替代 • 默认周期100ms适用大多数场景 |
| --cpu-quota   | -1     | 设置CPU CFS配额(单位:微秒)。与--cpu-period配合使用,quota/period的值等效于--cpus的值。 | • 不建议单独使用 • 建议使用--cpus替代 • 仅在需要精细调度时使用 |
| --cpuset-cpus | 无限制 | 指定容器可以使用的CPU核心编号,如"0,2"表示只能使用0号和2号CPU核心。 | • 适用于CPU绑核场景 • 可提高缓存命中率 • 注意预留系统CPU资源 |
| --cpuset-mems | 无限制 | 指定容器使用的NUMA节点。仅在NUMA架构服务器中有效。           | • 仅用于NUMA架构 • 需了解硬件架构再使用 • 一般场景不建议使用 |
| --cpu-shares  | 1024   | 设置CPU资源分配的权重值。在CPU竞争时,权重值越大获得更多CPU时间片。 | • 设置范围2-262144 • 仅在CPU竞争时有效 • 适合差异化CPU分配   |

> **最佳实践建议**：
>
> 1. 生产环境建议使用--cpus参数限制CPU使用
> 2. 按实际需求合理设置CPU限制,预留足够系统资源
> 3. 特殊场景(如CPU密集型)可考虑使用cpuset-cpus绑核
> 4. 避免过度限制导致容器性能问题

### 容器MEM限制

#### OOM异常

**OOM (Out Of Memory)**，即内存耗尽异常。当 Linux 系统**所有可用内存（包括物理内存和交换空间 Swap）都被用完**时，内核为了防止系统彻底崩溃，会启动一个机制来“救命”——**杀死 (Kill) 某些进程，强制释放内存**，这个过程就叫 **"OOM Killer"**。

> **为什么需要关注 Docker 容器的 OOM？** 
>
> 在一个运行着多个容器和其他应用的宿主机上，如果某个容器或应用疯狂占用内存，导致系统内存耗尽，OOM Killer 就会被触发。
>
> 1. **无差别攻击风险**：OOM Killer 会检查系统上的**所有进程**（包括 `dockerd` 本身、其他容器、系统关键进程等），并选择其中一个杀掉。这可能导致：
>    - 一个不重要的容器杀掉了数据库容器，导致核心服务宕机。
>    - `dockerd` 进程本身被杀死，导致**所有容器全部宕机**，这是最糟糕的情况。
> 2. **Docker 的应对策略**：为了降低这种风险，Docker 引擎 (`dockerd`) 采取了一个自我保护措施：**调整自身的 OOM 优先级**。它将自己的 `oom_score_adj` 设为一个较低的值，让自己变得“不那么容易被杀死”，从而保护整个容器生态的稳定。

#### OOM评分机制

系统到底根据什么来决定“杀死谁”呢？答案是 **OOM 评分 (oom_score)**

系统会为每个进程计算一个分数，分数最高的进程就是最先被牺牲的那个

| 参数名              | 作用         | 取值范围          | 说明                                                         |
| ------------------- | ------------ | ----------------- | ------------------------------------------------------------ |
| **`oom_score`**     | **最终得分** | **0 到 1000+**    | **这是系统计算的最终结果。分数越高，进程被杀死的优先级就越高。你无法直接修改它，它由系统根据以下因素自动计算：** • **内存消耗**：进程占用的内存越多，分数越高。 • **运行时间**：运行时间越短的进程（“新人”），分数越高，越容易被牺牲。 • **进程类型**：特权进程分数会较低。 • **`oom_score_adj` 设置**：受此参数调整。 |
| **`oom_score_adj`** | **调整分数** | **-1000 到 1000** | **这是我们可以手动调整的关键参数，用于影响最终的 `oom_score`。** • **设为 -1000**：进程**几乎免疫**，永远不会被 OOM Killer 杀死。 • **设为 0**：不调整，使用系统默认计算方式。 • **设为正数**：增加被杀死的概率，值越大越容易被杀。 • **设为负数**：降低被杀死的概率，值越小（越负）越安全。 |
| `oom_adj` (已过时)  | 旧版调整参数 | -17 到 +15        | 为了兼容旧版本内核，功能类似 `oom_score_adj`。**现代系统应使用 `oom_score_adj`。** |

> **最佳实践建议**：
>
> 1. 为关键进程适当降低OOM评分，避免被意外kill
> 2. 定期监控高内存进程的oom_score
> 3. 合理规划内存使用，避免触发OOM
> 4. 使用容器时建议设置内存限制

| -------------------- | ---------------------------------- | ------------ | ------------------------------------------------------------ |

>
> 1. 生产环境必须设置-m参数限制内存使用
> 2. 建议禁用或限制swap使用
> 3. 合理设置memory-reservation作为预警
> 4. 谨慎使用kernel-memory和oom-kill-disable

# 容器编排

## docker compose

Docker Compose 是一个用来“一键”启动和管理多个有关联的容器的工具。我们只需要在一个配置文件中定义好这些容器是什么、怎么配置、如何互通，然后一条命令就能让整个应用栈跑起来

## 为何需要？

一个简单的应用可能只有一个容器（比如一个网站）。但一个稍微真实点的应用（比如一个Web项目），通常由多个**服务**组成，例如：

1. **Web 服务器**：比如一个 Python 或 Node.js 应用（一个容器）
2. **数据库**：比如 MySQL 或 Redis（另一个容器）
3. **缓存服务**：比如 Redis（又一个容器）

> **手动管理的痛点：** 
>
> - **命令又长又复杂**，容易出错。
> - **容器启动顺序**很重要（Web应用需要先等数据库启动好），手动保证很麻烦。
> - 管理和维护困难，尤其是需要重启或重建时。
>
> **Docker Compose 解决了这些问题：** 
>
> - **声明式配置**：所有容器的启动参数都写在一个文件里（`docker-compose.yml`），清晰明了。
> - **一键操作**：一条命令（`docker compose up`）就能启动所有容器，并自动处理好它们之间的网络、依赖关系。
> - **高效管理**：一条命令可以停止、删除、重建所有相关容器。

## 项目结构

Docker Compose 项目将所管理的容器分为三层，分别是：

- **工程（Project）**：工程是 Docker Compose 管理的最高层级，通常对应一个包含多个服务的应用场景。一个工程可以包含多个服务，这些服务通过 `docker-compose.yml` 文件进行定义。
- **服务（Service）**：服务是工程中的一个逻辑单元，通常对应一个容器模板。服务定义了容器的镜像、环境变量、端口映射等配置。一个服务可以启动多个容器实例。
- **容器（Container）**：容器是服务的具体运行实例。Docker Compose 会根据服务的定义创建并管理容器。

通过这种分层结构，Docker Compose 能够高效地管理和编排多个容器，简化复杂的容器依赖关系，提高开发和部署效率

## 部署过程

### 编写YAML文件

**`docker-compose.yml` 文件** 

这个文件是 Compose 的核心，它用 **YAML** 格式定义了整个应用需要的**服务、网络、数据卷** 

以下是编写格式以及常用配置项

```yaml
# docker-compose.yml
# 说明：YAML 文件使用缩进表示层级关系，建议使用2个空格进行缩进，不要使用Tab键

# 指定 Docker Compose 文件的版本。
# 版本号需要与安装的 Docker Engine 版本兼容。
# 建议使用较新的版本（如 3.8）以支持更多功能。
version: '3.8'

# 定义本项目所包含的所有服务（容器）。
# 每个服务都会在运行时分隔成独立的容器。
services:

  # 服务名称：由用户自定义，如 'web', 'db', 'cache'等。
  # 该名称将作为容器的默认前缀和网络中的主机名。
  webapp:
    # 指定构建镜像的上下文路径。可以是包含 Dockerfile 的目录路径，或者一个指向 Git 仓库的 URL。
    # 如果使用相对路径，则相对于当前 docker-compose.yml 文件的位置。
    build:
      context: . # 构建上下文路径，通常为当前目录 '.'
      dockerfile: Dockerfile # 指定 Dockerfile 文件名，默认为 'Dockerfile'
      args: # 构建时传递给 Dockerfile 的参数，类似于 docker build --build-arg
        - BUILD_ENV=production

    #  Alternatively, if you are using a pre-built image from a registry:
    #  image: username/repository:tag  (e.g., nginx:alpine, mysql:8.0, redis:latest)

    # 设置容器启动时运行的命令，覆盖 Dockerfile 中的 CMD 指令。
    command: python app.py

    # 设置容器重启策略，以应对容器退出的情况。
    # no:        默认，不自动重启
    # always:    总是重启
    # on-failure:仅在非0状态退出时重启
    # unless-stopped: 总是重启，除非用户手动停止
    restart: unless-stopped

    # 设置容器依赖关系。Compose 会先启动并确保依赖的服务就绪后，再启动本服务。
    # 注意：这只能控制启动顺序，并不能等待依赖服务（如数据库）真正“可用”。
    depends_on:
      - database
      - redis

    # 设置容器需要暴露的端口，格式为 [HOST:]CONTAINER。
    # 仅使用 CONTAINER 端口时，端口会随机映射到主机的一个高端口。
    ports:
      - "8000:5000"  # 将宿主机的8000端口映射到容器的5000端口
      - "8443:443"   # 宿主机的8443 -> 容器的443

    # 将容器内的路径挂载到主机或其他容器。
    # 格式： [HOST:CONTAINER] 或 [命名卷:CONTAINER]
    volumes:
      - ./app:/code/app  # 挂载主机当前目录下的app文件夹到容器的/code/app (常用于代码开发，实时同步)
      - logs:/app/logs   # 使用下面定义的命名卷 'logs'，挂载到容器的/app/logs (常用于持久化数据)
      - /etc/localtime:/etc/localtime:ro # 挂载主机时间到容器，只读 (ro)

    # 设置容器连接的网络。可以连接到下方自定义的网络，以实现服务隔离。
    networks:
      - frontend-tier
      - backend-tier

    # 设置容器内的环境变量。
    # 可以使用数组或字典格式。敏感信息强烈建议使用 '.env' 文件或 Docker secrets。
    environment:
      - NODE_ENV=production
      - DATABASE_HOST=database # 使用服务名作为主机名，Compose会自动进行DNS解析
      - REDIS_HOST=redis
    #   environment:
    #     NODE_ENV: production
    #     DATABASE_HOST: database

    # 从文件（通常是 .env）中注入环境变量。
    env_file:
      - .env # 默认从当前目录下的 .env 文件读取
      - ./secrets.env # 可以指定多个文件

  # 数据库服务示例
  database:
    image: postgres:13-alpine # 使用官方的 PostgreSQL 镜像
    restart: unless-stopped
    # 设置数据卷，确保数据库数据持久化，不会随容器删除而丢失。
    volumes:
      - postgres_data:/var/lib/postgresql/data # 使用命名卷
    environment:
      - POSTGRES_DB=mydb
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=secretpassword # 生产环境中请使用 secrets 管理密码！
    networks:
      - backend-tier # 只连接到后端网络，与前端隔离，更安全

  # Redis缓存服务示例
  redis:
    image: redis:6-alpine
    restart: unless-stopped
    command: redis-server --requirepass myredispassword # 带密码启动
    volumes:
      - redis_data:/data
    networks:
      - backend-tier

# 定义本项目中所使用的所有命名卷。
# 卷是持久化数据的最佳方式，由 Docker 管理存储位置。
volumes:
  postgres_data: # 上面 services.database.volumes 中引用的卷
    driver: local # 使用本地驱动
  redis_data:    # 上面 services.redis.volumes 中引用的卷
  logs:          # 上面 services.webapp.volumes 中引用的卷

# 定义本项目中所使用的自定义网络。
# 创建自定义网络可以更好地控制服务间的通信（DNS发现、子网等）。
networks:
  frontend-tier: # 前端网络，可能用于连接Web服务器和负载均衡器
    driver: bridge
  backend-tier:  # 后端网络，用于连接Web服务器、数据库、缓存等，与外界隔离
    driver: bridge
    # 可以配置更多网络选项
    # internal: true # 如果设置为true，则此网络完全与外界隔离

# 其他不常用但重要的配置项（可选）：
# configs:    # 用于向服务注入非敏感的配置文件（Swarm模式下更常用）
# secrets:    # 用于以安全的方式向服务注入敏感信息（如密码、密钥），优于环境变量
```

### 常用命令

> **注意**：
>
> 在旧版 Docker 中，docker compose作为独立的命令行工具使用，也就是需要使用 `docker-compose` 这个命令行工具来使用对应命令
>
> 而从 Docker 20.10 版本开始，Docker Compose 被集成到了 Docker 中，作为插件使用，而不是独立的命令行工具，所以说在20以后的版本中，我们直接使用docker compose(中间用空格隔开)即可

#### docker compose up

创建并启动容器、网络、卷等所有资源

```shell
docker compose up [选项] [服务...]
```

**选项**

- **-d, --detach**：后台运行容器
- **--build**：在启动前重新构建镜像
- **--force-recreate**：强制重新创建容器，即使配置未更改
- **--no-deps**：不启动依赖的服务
- **--remove-orphans**：删除未在compose文件中定义的容器
- **--scale SERVICE=NUM**：设置服务运行的容器数量

> **注意**
>
> 1. 默认在前台运行，输出所有容器的日志
> 2. 使用-d选项可在后台运行
> 3. 会自动构建Dockerfile中定义的镜像
> 4. 首次运行时会创建所有定义的网络和卷
> 5. 服务名称可省略，默认启动所有服务

#### docker compose down

停止并删除容器、网络等资源

```shell
docker compose down [选项]
```

**选项**

- **-v, --volumes**：同时删除compose文件中定义的匿名卷
- **--remove-orphans**：删除未在compose文件中定义的容器
- **-t, --timeout**：设置停止超时时间（单位：秒）

> **注意**
>
> 1. 默认不会删除卷，防止数据丢失
> 2. 使用-v选项会删除匿名卷，但不会删除命名卷
> 3. 网络会被自动删除
> 4. 容器停止后会被删除
> 5. 不会删除构建的镜像

#### docker compose ps

列出项目中的所有容器

```shell
docker compose ps [选项] [服务...]
```

**选项**

- **-a, --all**：显示所有容器，包括已停止的
- **--quiet**：只显示容器ID
- **--services**：显示服务名称
- **--filter KEY=VAL**：根据条件过滤容器

> **注意**
>
> 1. 默认只显示运行中的容器
> 2. 显示信息包括容器名称、命令、状态、端口
> 3. 服务名称可省略，默认显示所有服务
> 4. 容器名称格式为"项目名_服务名_序号"
> 5. 状态包括running、exited、paused等

#### docker compose logs

查看服务的日志输出

```shell
docker compose logs [选项] [服务...]
```

**选项**

- **-f, --follow**：跟踪日志输出
- **--tail**：从日志末尾显示的行数（默认所有）
- **-t, --timestamps**：显示时间戳
- **--no-color**：不显示颜色

> **注意**
>
> 1. 默认显示所有服务的日志
> 2. 可以指定特定服务查看日志
> 3. 日志按时间顺序合并显示
> 4. 使用-f选项可以实时查看日志
> 5. 不会显示已停止容器的历史日志

#### docker compose stop

停止正在运行的容器，但不删除

```shell
docker compose stop [选项] [服务...]
```

**选项**

- **-t, --timeout**：设置停止超时时间（单位：秒，默认10秒）

> **注意**
>
> 1. 容器停止后仍可重新启动
> 2. 容器配置和数据保持不变
> 3. 网络和卷不会被删除
> 4. 服务名称可省略，默认停止所有服务
> 5. 使用docker compose start可重新启动

#### docker compose start

启动已停止的容器

```shell
docker compose start [服务...]
```

> **注意**
>
> 1. 只能启动已存在但已停止的容器
> 2. 使用原有配置启动容器
> 3. 不会重新构建镜像
> 4. 不会创建新的网络或卷
> 5. 服务名称可省略，默认启动所有已停止的服务

#### docker compose restart

重启容器

```shell
docker compose restart [选项] [服务...]
```

**选项**

- **-t, --timeout**：设置停止超时时间（单位：秒，默认10秒）

> **注意**
>
> 1. 会先停止容器再重新启动
> 2. 容器将使用最初创建时的相同配置重新启动
> 3. 对已停止的容器执行会直接启动它
> 4. 重启期间服务会有短暂中断
> 5. 适用于配置更新后需要重新加载的场景

#### docker compose build

构建或重新构建服务的镜像

```shell
docker compose build [选项] [服务...]
```

**选项**

- **--build-arg key=val**：设置构建时的变量
- **--no-cache**：构建时不使用缓存
- **--pull**：总是尝试拉取更新版本的镜像

> **注意**
>
> 1. 只构建镜像，不会启动服务
> 2. 基于Dockerfile构建镜像
> 3. 构建的镜像会用于后续的docker compose up
> 4. 服务名称可省略，默认构建所有服务
> 5. 使用--no-cache确保全新的构建

#### docker compose exec

在运行的容器中执行命令

```shell
docker compose exec [选项] 服务 命令 [参数...]
```

**选项**

- **-d, --detach**：在后台运行命令
- **--env KEY=VAL**：设置环境变量
- **-u, --user**：以指定用户身份运行
- **-T**：不分配TTY

> **注意**
>
> 1. 只能在运行中的容器中执行命令
> 2. 默认在当前项目的第一个容器中执行
> 3. 常用命令如：docker compose exec app sh
> 4. 使用-d选项可执行后台任务
> 5. 退出码与执行的命令一致

#### docker compose pull

拉取服务依赖的镜像

```shell
docker compose pull [选项] [服务...]
```

**选项**

- **--ignore-pull-failures**：忽略拉取失败的镜像
- **--quiet**：只显示错误信息

> **注意**
>
> 1. 只拉取镜像，不会启动服务
> 2. 对于build构建的服务无效
> 3. 服务名称可省略，默认拉取所有服务
> 4. 拉取完成后可使用docker compose up启动
> 5. 使用前确保docker login已登录

# 存储引擎

Docker 存储引擎是 Docker 容器管理文件系统的核心组件，负责镜像层与容器层的组织、读写操作及资源隔离。其核心在于通过**联合文件系统（UnionFS）**和**写时复制（Copy-on-Write, CoW）**机制实现高效存储管理

## 分层存储与联合挂载

Docker镜像由多个只读层（Layer）叠加而成，容器运行时会在镜像层之上创建可写层。所有层通过 UnionFS 联合挂载到同一视图，上层文件覆盖下层同名文件，但底层数据保持不变

UnionFS（联合文件系统）是一种分层、轻量级且高性能的文件系统技术，通过将多个目录（分支）联合挂载到同一目标目录，形成统一的文件系统视图。核心机制如下:

- **分层存储**：UnionFS 通过分层结构管理文件，每个层（分支）可以是只读或可写。不同层中相同路径的文件会被上层覆盖，但底层内容保持不变
- **只读层和可写层**：只读层通常为基础镜像或依赖文件，不可修改；可写层：容器运行时新增的层，所有修改均在此层记录

## 写时复制（CoW）机制

当容器需要修改文件时，存储引擎将文件从底层只读层复制到可写层进行修改，而非直接修改原始数据。这种机制减少冗余存储，允许多容器共享同一镜像层，显著降低磁盘占用

### 工作原理

- **联合挂载（Unio Mount）**：将多个物理目录（如目录A和B）挂载到同一虚拟目录（如目录C），合并后的视图包含所有分支目录的内容。若存在同名文件，优先显示上层文件
- **访问优先级**：用户访问文件时，UnionFS按层从上至下搜索，返回第一个匹配的文件。例如，可写层优先级高于只读层
- **数据隔离与共享**：不同容器共享同一基础镜像层，但各自的可写层独立，实现资源复用与运行时隔离

## 主流存储引擎

Docker支持多种存储驱动，不同驱动在性能、稳定性、适用场景上存在差异：

| 存储驱动      | 特点                                                         | 优势                                                         | 局限性                                                   | 适用场景                                                     |
| ------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | -------------------------------------------------------- | ------------------------------------------------------------ |
| OverlayFS     | • Linux内核原生支持（≥3.18） • 使用overlay2驱动 • 仅需一个只读层和一个可写层 • 结构简单且性能优异 | • 启动速度快 • 适合生产环境 • 支持高效的文件系统层叠 • 节省存储空间 | • 层数限制（通常≤127层） • 频繁小文件写入可能增加I/O开销 | • 通用容器环境 • 需要高性能的生产系统 • 对存储空间敏感的场景 |
| AUFS          | • 通过多层联合挂载实现CoW • 稳定性较好 • 未集成到内核，需额外安装 | • 内存利用率高 • 适合旧版Linux系统                           | • 高并发写入性能较差 • 逐渐被OverlayFS替代               | • 旧版Linux系统 • 对内存资源敏感的环境 • 低并发写入场景      |
| Device Mapper | • 基于块设备映射 • 使用"thin pool"技术 • 支持动态扩容        | • 支持精细的存储控制 • 适合块级存储需求 • 动态扩容能力强     | • 配置复杂 • 需预分配存储池 • 可能导致空间浪费           | • 数据库容器 • 需要精细存储控制的场景 • 大规模存储系统       |
| Btrfs/ZFS     | • 支持高级功能（快照/去重/压缩） • 文件系统级别的功能丰富    | • Btrfs写入密集型场景表现优异 • ZFS提供数据完整性校验 • 支持高效压缩 | • 对系统内核版本依赖性强 • 稳定性与兼容性需验证          | • 需要数据快照功能 • 写入密集型应用 • 对数据完整性要求高的场景 |
