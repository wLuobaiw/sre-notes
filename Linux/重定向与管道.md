
# 标准输入/输出/错误

Linux 中每个进程默认打开三个文件描述符（FD）：

| FD | 名称 | 默认目标 | 说明 |
|----|------|---------|------|
| 0 | stdin（标准输入） | 键盘 | 进程读取数据的地方 |
| 1 | stdout（标准输出） | 终端 | 进程正常输出的地方 |
| 2 | stderr（标准错误） | 终端 | 进程输出错误信息的地方 |

stdout 和 stderr 都默认输出到终端，但它们**是两个独立的通道**——这正是我们能分别控制它们的原因。

# 输出重定向

## 基本语法

```shell
command > file           # stdout 覆盖写入 file
command >> file          # stdout 追加写入 file
command 2> file          # stderr 覆盖写入 file
command 2>> file         # stderr 追加写入 file
```

## 同时处理 stdout 和 stderr

这是运维中最常用的场景——脚本运行时既要看输出，也要记录错误。

```shell
# 分别输出到不同文件
command > stdout.log 2> stderr.log

# 合并输出到同一个文件
command > all.log 2>&1
command &> all.log               # bash 简写，效果同上

# 追加模式合并
command >> all.log 2>&1
command &>> all.log              # bash 简写

# 只关心错误，忽略正常输出
command > /dev/null 2> stderr.log
command 1>/dev/null 2>stderr.log  # 显式写法
```

## 理解 `2>&1`

`2>&1` 的意思是"把 FD 2（stderr）指向 FD 1（stdout）当前指向的位置"。它不是"把 stderr 变成 stdout"，而是**复制文件描述符的指向**。

```shell
# ✓ 正确：stdout 先改到 file.log，然后 stderr 复制 stdout 的指向 → 都进 file.log
command > file.log 2>&1

# ✗ 错误：stderr 先复制了 stdout 的当前指向（终端），然后 stdout 才改到文件
command 2>&1 > file.log          # stderr 仍然输出到终端！
```

**记忆法则**：`> file` 在前，`2>&1` 在后——先决定 stdout 去哪，再让 stderr 跟着去。

## 丢弃输出——/dev/null

`/dev/null` 是一个特殊的设备文件——写入它的所有数据都会被**直接丢弃**，读取它永远返回 EOF。

```shell
# 丢弃所有输出（最常用）
command > /dev/null 2>&1

# 只丢弃错误，保留正常输出
command 2>/dev/null

# 只丢弃正常输出，保留错误
command > /dev/null

# 后台运行不产生任何终端输出
nohup command > /dev/null 2>&1 &

# 验证脚本——只要退出码，不看输出
if command > /dev/null 2>&1; then
    echo "成功"
fi
```

## 快速参考——日志场景对照表

| 需求 | 命令 |
|------|------|
| 正常运行，记录所有日志 | `./app > app.log 2>&1` |
| 后台运行，不刷屏 | `./app > app.log 2>&1 &` |
| 只保留错误日志 | `./app > /dev/null 2> error.log` |
| 只看屏幕输出，不存文件 | `./app 2>&1 \| tee app.log` |
| 彻底静默 | `./app > /dev/null 2>&1` |
| 追加写入已有日志 | `./app >> app.log 2>&1` |
| cron 中记录日志 | `0 2 * * * /backup.sh >> /var/log/backup.log 2>&1` |

# 输入重定向

```shell
command < file                   # 从文件读取 stdin
command <<< "string"             # here-string（bash）
```

## Here Document——嵌入多行文本

```shell
command << 'EOF'
第一行
第二行
EOF
```

结束标记必须**单独一行、顶格写**。标记加引号（`'EOF'`）会阻止变量展开：

```shell
cat << EOF
当前用户: $USER           # 变量会被展开
当前目录: $(pwd)
EOF

cat << 'EOF'
$USER 不会被展开，原样输出
EOF
```

常见用途：脚本中生成配置文件、给命令传递多行输入。

```shell
# 追加内容到文件
cat << 'EOF' >> /etc/hosts
192.168.1.10 db-server
192.168.1.11 cache-server
EOF

# 通过 SSH 执行多行远程命令
ssh user@host << 'EOF'
cd /opt/app
git pull
systemctl restart app
EOF
```

# 管道（Pipe）

管道 `|` 将前一个命令的 **stdout** 直接传给后一个命令的 **stdin**。两个命令**并发执行**，数据在内存中传递，不经过磁盘。

```shell
ls -l | grep '.txt'
cat access.log | grep '404' | awk '{print $1}' | sort | uniq -c | sort -rn
```

## 管道与 stderr

管道**只传递 stdout**，stderr 不会进入管道：

```shell
# stderr 不在管道中——error 消息仍输出到终端
command | grep 'pattern'

# 合并后传入管道
command 2>&1 | grep 'pattern'

# 只传递 stderr，丢弃 stdout
command 2>&1 1>/dev/null | grep 'error'
```

## tee——分流输出

同时将输出写入文件和传给管道：

```shell
command | tee file.log           # 写入文件 + 传给管道
command | tee -a file.log        # 追加模式
command 2>&1 | tee all.log       # 同时捕获 stdout 和 stderr

# 典型场景：构建时既看输出又保存日志
./build.sh 2>&1 | tee build.log
```

## xargs——stdin 转命令行参数

某些命令不接受 stdin（如 `rm`、`echo`），xargs 将 stdin 转换为命令行参数：

```shell
find . -name '*.log' | xargs rm
find . -name '*.log' -print0 | xargs -0 rm    # 文件名含空格时用这个
echo {1..10} | xargs -n 3                      # 每 3 个一组
find . -name '*.tmp' | xargs -p rm             # -p 交互确认
```

xargs 将多个参数打包成一个命令执行，远比 `-exec \;` 高效。

## 管道 vs 重定向 vs tee

| | 重定向 `>` | 管道 `\|` | tee |
|---|---|---|---|
| 数据流向 | 进程 → 文件 | 进程 → 进程 | 进程 → 文件 + 进程 |
| 终端可见？ | 否 | 否（末端的 stdout 可见） | 是 |
| 落盘？ | 是 | 否 | 是 |

# 实际场景演练

## 场景1：后台运行并记录日志

```shell
# 简单版：输出全进文件，终端不显示
./myapp > app.log 2>&1 &

# 完整版：带时间戳的日志
./myapp 2>&1 | while read line; do echo "$(date '+%Y-%m-%d %H:%M:%S') $line"; done > app.log &
```

## 场景2：查看日志中的错误

```shell
# 只看错误
grep -E 'ERROR|FATAL' /var/log/app.log

# 实时追踪错误
tail -f /var/log/app.log | grep --line-buffered 'ERROR'

# 统计各类错误数量
grep -oE '(ERROR|WARN|INFO|DEBUG)' app.log | sort | uniq -c
```

> 日志轮转、journalctl 等日志管理内容见 [日志管理](./系统服务/日志管理.md)。

## 场景3：cron 中可靠记录输出

```shell
# cron 中默认没有终端——必须显式重定向
0 2 * * * /opt/backup.sh >> /var/log/backup.log 2>&1

# 只记录失败（正常输出丢弃）
0 2 * * * /opt/backup.sh > /dev/null 2>> /var/log/backup_error.log
```

## 场景4：静默检查——只要退出码

```shell
# 检查命令是否成功，不需要看输出
if pgrep nginx > /dev/null 2>&1; then
    echo "nginx 正在运行"
else
    echo "nginx 未运行"
    systemctl start nginx
fi
```

# 注意事项

- 管道只传递 stdout——stderr 不会自动进入管道，需要 `2>&1`
- 管道中的命令运行在子 shell 中——变量修改不会影响父 shell
- 记日志用 `>>` 追加而非 `>` 覆盖——除非你确定要清空旧日志
- `/dev/null` 是"数据黑洞"——写入即丢弃，安全无害
- `2>&1` 的顺序至关重要——`> file` 必须在 `2>&1` **之前**
