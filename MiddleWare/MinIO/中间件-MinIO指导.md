# 阶段1：背景与起源

## 它是什么

**MinIO 是一款开源、高性能、兼容 Amazon S3 API 的分布式对象存储系统。**

它在技术栈中的位置：处于**存储层**，专门用来存放**非结构化数据**（图片、视频、日志文件、备份文件、文档等等）。

## 为什么出现

在 MinIO 出现之前，做"海量非结构化数据存储"主要有两个选择：

**路线一：传统文件系统/NAS（网络附加存储）**

- **扩展性差**：一台服务器硬盘满了，无法简单地"加一台就能继续用"
- **单点瓶颈**：这台机器挂了，所有文件都无法访问
- **性能瓶颈**：大量并发访问时，磁盘 I/O 成为瓶颈

**路线二：Hadoop HDFS（分布式文件系统）**

- **部署和维护极重**：需要 NameNode、DataNode、ZooKeeper 等一堆组件，强依赖 Java 生态
- **小文件噩梦**：小文件（KB 级）的 I/O 效率极低，元数据会撑爆 NameNode 内存
- **笨重**：整个体系是为"一次写入、多次读取"的大文件设计的，不适合频繁的增删改

同时，云计算时代 **Amazon S3** 凭借简单的 HTTP API 和近乎无限的扩展能力，成为对象存储的**事实标准**。但很多企业因**数据合规、成本控制、数据主权**等原因，不能把数据放在公有云上，需要在自有服务器上搭建一个"像 S3 一样好用、但又轻量、高性能"的存储系统。

## 它解决什么

MinIO 的核心定位：**私有化的 S3 替代品**。

- 完全兼容 S3 API（为 S3 写的代码和工具都能直接用）
- 轻量到极致（一个二进制文件，无外部依赖）
- 性能针对现代硬件（NVMe 固态硬盘、万兆网络）做专门优化
- 部署极简（一行命令就能起一个集群）

> **类比**：如果把 Amazon S3 比作"公有云盘服务"，那 MinIO 就是你可以部署在自家服务器上的"私有云盘系统"，接口和 S3 一模一样。

# 阶段2：核心概念

MinIO 的核心概念一共五个：

## 1. 服务端（MinIO Server）与 客户端（MinIO Client, mc）

- **服务端**：真正负责"存文件、取文件"的服务程序。它是 MinIO 的核心，部署在服务器上持续运行，监听 HTTP 请求。
- **客户端（mc）**：一个命令行工具，用来"遥控"服务端。比如创建桶、上传文件、查看文件列表等。

> **类比**：这和 MySQL 很像——`mysqld` 是服务端（存数据、处理 SQL），`mysql` 命令行是客户端（发 SQL 去操作数据库）。MinIO Server 就是对象存储界的 `mysqld`，`mc` 就是对象存储界的 `mysql` 命令行。

## 2. 对象（Object）

**对象是 MinIO 中存储的基本单元。** 你在 MinIO 里存的每一个文件，就是一个对象。

一个对象包含三部分：

| 组成部分         | 说明                                                 | 类比 MySQL     |
| :--------------- | :--------------------------------------------------- | :------------- |
| **数据本身**     | 就是文件内容（一张图片、一个PDF、一段视频）           | 一行数据的值   |
| **元数据**       | 描述这个文件的信息（文件名、大小、类型、上传时间等） | 字段名和类型   |
| **唯一标识（Key）** | 对象在桶中的唯一"路径名"，如 `photos/2024/vacation.jpg` | 主键 ID        |

> **注意**：虽然 Key 长得像文件路径（有 `/` 分隔符），但 MinIO 内部是**扁平结构**，没有真正的"文件夹层级"。`/` 只是视觉上模拟了目录树，方便组织管理。

## 3. 桶（Bucket）

**桶是组织对象的容器。** 可以理解为一个"顶级文件夹"。

| 特性       | 说明                                           |
| :--------- | :--------------------------------------------- |
| 命名规则   | 必须全局唯一、小写字母+数字+连字符             |
| 容量限制   | 桶内的对象数量**没有限制**                     |
| 独立配置   | 每个桶可以单独设置访问权限、版本控制、生命周期等 |

> **类比**：Bucket 之于 MinIO，就像 **Database（数据库）** 之于 MySQL。你在 MySQL 里创建多个数据库来隔离不同业务的数据；在 MinIO 里创建多个桶来隔离不同业务场景的文件。

## 4. 访问密钥（Access Key & Secret Key）

- **Access Key**：相当于"用户名"
- **Secret Key**：相当于"密码"

这两个密钥成对使用。MinIO 通过它们来验证每一次 API 请求的合法性。

> **类比**：就是 MinIO 版的"账号密码"，和 MySQL 的 `root/password` 是同一个概念。

## 5. 区域（Region）

区域用于标识桶所在的物理位置，默认值是 `us-east-1`（和 S3 保持一致）。

单机学习中基本用不到，但在**多机房部署**场景下，可以用不同 Region 区分北京机房和上海机房的 MinIO 集群。

## 五个概念的总结

```text
Access Key + Secret Key（身份凭证）
        │
        ▼
   ┌─────────┐
   │  MinIO  │  →  服务端（存文件的地方）
   │  Server │
   └─────────┘
        │
        ├── Bucket A（桶A，如：用户头像）
        │     ├── Object: avatars/user1.jpg
        │     └── Object: avatars/user2.jpg
        │
        └── Bucket B（桶B，如：系统日志）
              ├── Object: logs/2024-05-01.log
              └── Object: logs/2024-05-02.log
```

# 阶段3：原理及架构

## 一句话原理

**MinIO 把硬盘上的目录和文件当作"对象"，通过 HTTP RESTful API 暴露出去，底层用纠删码（Erasure Coding）而不是传统多副本或 RAID 来保证数据安全。**

## 组成组件

MinIO 的架构非常简单，不依赖任何外部组件：

| 组件              | 职责                                                         |
| :---------------- | :----------------------------------------------------------- |
| **MinIO Server**  | 核心存储引擎，负责数据读写、纠删码编解码、S3 API 响应        |
| **磁盘/目录**     | 实际存储数据的地方，每个节点可以挂载多块磁盘                 |
| **Erasure Set**   | 一组磁盘的逻辑集合，数据分片+校验块分散写入这个集合          |
| **mc 客户端**     | 管理员操作工具，与 Server 通过 HTTP 通信                     |

> **对比**：ZooKeeper 需要 Leader/Follower/Observer 多角色协作，Nacos 需要 MySQL 存配置。而 MinIO **没有任何主从角色、不需要外部数据库**，每个节点都是对等的，这是它部署极简的根本原因。

## 架构简图

```text
                    客户端请求（S3 API / mc 命令）
                              │
                              ▼
              ┌───────────────────────────┐
              │      负载均衡 / Nginx      │
              └───────────────────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          │                   │                   │
          ▼                   ▼                   ▼
   ┌────────────┐      ┌────────────┐      ┌────────────┐
   │  Node-1    │      │  Node-2    │      │  Node-3    │      ...
   │            │      │            │      │            │
   │ disk1 disk2│      │ disk1 disk2│      │ disk1 disk2│
   └────────────┘      └────────────┘      └────────────┘
          │                   │                   │
          └───────────────────┼───────────────────┘
                              │
                    所有磁盘组成 Erasure Set
                    （数据 + 校验块分散存储）
```

**文字说明**：每个 MinIO 节点都是对等的（无主从之分）。客户端请求打到任意一个节点都可以。所有节点的所有磁盘共同组成一个逻辑存储池——数据被切成数据块和校验块，分散写到不同磁盘上，任何一个节点宕机都不影响集群正常服务。

## 纠删码（Erasure Coding）—— 核心保护机制

这是 MinIO 最核心的技术，也是它和传统三副本方案最大的区别。

### 传统三副本怎么存？

```
文件: [A][B][C][D]  大小 100MB

节点1: [A][B][C][D]  100MB（副本1）
节点2: [A][B][C][D]  100MB（副本2）
节点3: [A][B][C][D]  100MB（副本3）

总占用: 300MB
容错能力: 最多坏 2 个节点
```

### 纠删码怎么存（以 8 块盘为例）？

```
文件: [A][B][C][D]  大小 100MB

切成 4 个数据块: [A][B][C][D]  各 25MB
算出 4 个校验块: [P1][P2][P3][P4]  各 25MB

分散写到 8 块盘:
disk1: [A]    disk2: [B]    disk3: [C]    disk4: [D]
disk5: [P1]   disk6: [P2]   disk7: [P3]   disk8: [P4]

总占用: 200MB
容错能力: 最多坏 4 块盘（任一节点宕机或任意 4 块盘损坏）
```

### 直观对比

| 对比维度     | 纠删码（MinIO）              | 三副本（传统方案）   |
| :----------- | :--------------------------- | :------------------- |
| **存储效率** | 50%（100MB 数据占用 200MB）  | 33%（100MB 占 300MB） |
| **容错能力** | 8 盘中坏 ≤4 盘数据不丢       | 3 副本中坏 ≤2 份不丢 |
| **恢复速度** | 快（从多个盘中并行重建）     | 较慢（从单个副本拷贝） |
| **CPU 开销** | 较高（需要编解码计算）       | 极低                  |

> **关键规则**：只要在线磁盘数 ≥ `总磁盘数/2 + 1`，集群就能正常读写。比如 8 块盘，至少 5 块在线即可。

## 高可用如何保证？

1. **节点宕机**：自动把请求转发到剩余健康节点
2. **磁盘损坏**：后台自动从其他盘的校验块重建丢失的数据
3. **最小集群**：至少 2 节点、每节点至少 2 盘（生产环境建议 ≥4 节点、每节点 ≥4 盘）

> **注意**：如果集群规模太小（比如只有 2 个节点），一旦坏了一个节点，只剩一个节点在线，已经没有冗余了，再坏就丢数据。所以生产环境至少 4 节点起步。
