
# 是什么

etcd 是一个**分布式、高可用的键值存储**，由 CoreOS 开发，与 Kubernetes 是独立项目。它在 Kubernetes 中充当**所有集群数据的唯一真相源**：节点列表、Pod 配置、Service 定义、Secret、ConfigMap……一切都在 etcd 中。

# 部署拓扑

etcd 本身是一个独立的分布式集群。生产环境通常有 3 或 5 个 etcd 节点。从 Kubernetes 角度看，etcd 是一个逻辑整体 —— apiserver 连接 etcd 集群的地址列表，对底层多节点无感知。

## 堆叠式

etcd 和 apiserver 运行在同一组机器上。每台 Master 节点同时跑 apiserver 和 etcd。省略额外机器，适合小集群。

## 外部 etcd

etcd 独立部署在专用机器上。故障域隔离：etcd 出问题不影响 apiserver 节点本身的运行。大型生产集群推荐。

# Raft 共识算法

etcd 使用 **Raft 算法** 在多个节点间保证数据一致性。

## 角色

- **Leader**（主节点）：有且只有一个，负责处理所有写请求
- **Follower**（从节点）：其余都是 Follower，只接收 Leader 的数据复制

客户端写请求无论打到哪个节点，最终都会被转发到 Leader 处理。

## 多数派原则

**任何写操作必须得到多数节点（N/2 + 1）确认后才算提交成功。**

| 集群总节点数 N | 多数 = N/2+1 | 可承受宕机数 |
|-------------|-------------|-------------|
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

如果存活节点数不足多数，etcd 集群进入**只读模式**，无法写入。

## 为什么只用奇数节点

3 节点容忍 1 台故障。4 节点**同样只能**容忍 1 台故障（多数 = 3），但多花了一台机器的钱，没有提升可用性。偶数节点不增加容错能力，纯粹浪费。

## 宕机后两节点数据不一致怎么办？

Raft 设计上已杜绝此问题：
- 只有 Leader 能接受写入
- 一条日志只有被多数节点确认后才标记为"已提交"
- 选举新 Leader 时，日志最长的节点赢得选举

新 Leader 一定拥有所有已提交的数据，不存在"两节点数据差异无法判定"的困境。

# 两种读取模式

etcd 提供两种读取模式，供调用方按场景选择：

- **线性一致性读（Linearizable Read）**：Follower 先向 Leader 确认自己数据的时效性，然后返回。保证读到的一定是最新已提交数据。Kubernetes 关键路径使用此模式。
- **串行读（Serializable Read）**：Follower 直接返回本地数据，可能落后几十毫秒。性能更好，适合对一致性不敏感的场景。

# 为什么 Kubernetes 对 etcd 延迟极度敏感

1. **apiserver 的写请求是同步等待 etcd 响应的** —— etcd 一次慢，所有写操作阻塞
2. Controller、Scheduler、kubelet 通过 Watch 机制持续监听 etcd 变化 —— 延迟一大，所有组件的响应都迟钝
3. 类比：etcd 是集群的"心脏"。心跳慢了，全身都受影响

因此生产环境 etcd 的磁盘必须使用 **SSD**。机械硬盘的随机写延迟直接让集群响应变得不可接受。etcd 应部署在独立或隔离的物理资源上，避免与其他组件争抢 IO。
