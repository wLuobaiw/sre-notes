
# 是什么

容器运行时是真正负责**拉取镜像、创建容器、启停容器**的底层组件。[kubelet](kubelet.md) 通过 CRI 接口调用容器运行时，自身不直接操作容器。

# OCI 规范

容器运行时体系由 **OCI（Open Container Initiative）** 两个开放标准定义：

- **OCI Runtime Spec**：定义"怎样运行一个容器"。实现者：runc（最广泛）、crun、kata-containers
- **OCI Image Spec**：定义"镜像的格式"。确保 Docker 构建的镜像可以在 containerd 中运行

# 两代运行时

## 高层运行时

负责镜像管理（拉取、解压、存储）和通过 gRPC 对外暴露接口。kubelet 的 CRI 调用打到这里。

- **containerd**：CNCF 毕业项目，Docker 内部也在用它，是目前最广泛的高层运行时
- **CRI-O**：专为 Kubernetes 设计的轻量运行时，只实现 CRI，不做镜像构建

## 低层运行时

高层运行时调用低层运行时来真正创建容器进程。符合 OCI Runtime Spec。

- **runc**：最广泛，containerd 和 CRI-O 默认都调用它

# 调用链路

```
kubelet
   ↓ CRI（gRPC）
containerd / CRI-O    ← 高层运行时：镜像管理 + CRI 实现
   ↓ OCI Runtime Spec
runc                   ← 低层运行时：创建容器进程
   ↓ Linux namespace + cgroup
容器进程
```

# Kubernetes 为什么移除 Docker 支持

1.24 版本之前，Kubernetes 通过 **dockershim**（内置适配层）支持 Docker。链路为：

```
kubelet → CRI → dockershim → Docker → containerd → runc → 容器
```

Docker 本身调用 containerd 来管理容器。dockershim 在中间做 CRI 到 Docker API 的翻译。

问题：
1. Docker 是单体工具，不只做运行时（还有镜像构建、Docker Compose 等），Kubernetes 只用其中一小部分
2. 多一层 dockershim 翻译增加延迟和维护负担
3. CRI 才是 Kubernetes 的标准接口，直接对接 CRI 实现（containerd/CRI-O）更自然

移除后链路缩短为两层：

```
kubelet → CRI → containerd → runc → 容器
```

对于用户，Docker 构建的镜像仍然可以正常运行 —— 因为所有运行时都遵循 OCI Image Spec。

# Docker 的角色变化

Docker 不等于容器运行时。更准确地说，Docker 是一个**开发者工具**：
- `docker build`：构建镜像（containerd 不提供这个功能）
- `docker run`：本地调试运行
- `docker-compose`：编排

生产环境用 containerd 跑容器、用 Docker CLI 构建镜像，互不影响。
