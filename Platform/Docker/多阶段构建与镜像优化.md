# 多阶段构建

构建 Docker 镜像时，我们往往需要编译工具、SDK、头文件等构建依赖，但这些**不应该出现在最终运行的镜像里**——它们会膨胀镜像体积、增加攻击面。

## 传统做法的问题

以一个 Go 应用为例：

```dockerfile
# 单阶段构建：编译 + 运行全在同一个镜像
FROM golang:1.21
WORKDIR /app
COPY . .
RUN go build -o myapp .
CMD ["./myapp"]
```

**结果：镜像约 900MB**。因为 `golang:1.21` 镜像本身就包含 Go 编译器、标准库源码、git 等大量构建工具，这些在运行时完全用不上。

传统的"优化"手段是写两个 Dockerfile + 一个 shell 脚本手动串联——繁琐且容易出错。

## 基本语法

Docker 17.05 引入多阶段构建，允许在**一个 Dockerfile 中定义多个 `FROM`**，每个 `FROM` 开始一个新的构建阶段，最终只将需要的产物复制到最终镜像。

```dockerfile
FROM golang:1.21 AS builder          # 阶段1：编译阶段，命名为 builder
WORKDIR /app
COPY . .
RUN go build -o myapp .

FROM alpine:3.18                      # 阶段2：运行阶段（最终镜像）
WORKDIR /app
COPY --from=builder /app/myapp .      # 从 builder 阶段只拿编译产物
CMD ["./myapp"]
```

**结果：镜像约 15MB**。最终镜像基于 `alpine`，只包含一个可执行文件，没有任何编译工具。

## 多阶段构建的核心理念

```
┌─────────────────────────────────┐
│ 构建阶段（builder）              │
│   SDK / 编译器 / 依赖            │  ← 臃肿但只在构建时存在
│   源码 → 编译 → 产物             │
└──────────┬──────────────────────┘
           │ COPY --from=builder（只取产物）
           ▼
┌─────────────────────────────────┐
│ 运行阶段（最终镜像）             │
│   最小化运行时 + 编译产物         │  ← 干净、安全、体积小
└─────────────────────────────────┘
```

## 多阶段 + 多产物

一个 Dockerfile 可以有多个构建阶段，各自产生不同的产物：

```dockerfile
FROM node:18 AS frontend-builder
WORKDIR /app/frontend
COPY frontend/ .
RUN npm ci && npm run build          # 产出 dist/ 目录

FROM golang:1.21 AS backend-builder
WORKDIR /app/backend
COPY backend/ .
RUN go build -o server .

FROM alpine:3.18
WORKDIR /app
COPY --from=backend-builder /app/backend/server .
COPY --from=frontend-builder /app/frontend/dist ./static
CMD ["./server"]
```

## 复用阶段（`FROM ... AS` + 被引用）

命名阶段不仅可以被 `COPY --from` 引用，还可以被后续阶段 `FROM`：

```dockerfile
FROM alpine:3.18 AS base
RUN apk add --no-cache ca-certificates tzdata

FROM base AS builder
RUN apk add --no-cache build-base
# ... 编译操作

FROM base                        # 复用 base，不引入编译工具
COPY --from=builder /app/myapp .
CMD ["./myapp"]
```

# 层缓存与层数优化

## 镜像层是如何产生的

Dockerfile 中每条 `RUN`、`COPY`、`ADD` 指令都会创建一个新的只读层。层数越多，镜像越大，推送/拉取也越慢。

## 合并 RUN 指令

```dockerfile
# 差：每条 RUN 各产生一层，且 apt 缓存留在层中
RUN apt-get update
RUN apt-get install -y nginx
RUN apt-get install -y curl
RUN rm -rf /var/lib/apt/lists/*    # 这一行无法清理前面各层已写入的数据

# 好：合并为一条 RUN，在同一个层内完成安装+清理
RUN apt-get update && \
    apt-get install -y nginx curl && \
    rm -rf /var/lib/apt/lists/*
```

**关键原则**：在同一层中创建的文件，在同一层中删除，才不会残留在镜像里。

## 按变更频率排序

Docker 构建时，如果某一层发生变化，其**之后的所有层缓存都会失效**，必须重新构建。因此应将"最不容易变"的放在前面：

```dockerfile
# 好：依赖安装（不常变）→ 源码复制（经常变）
FROM node:18-alpine
WORKDIR /app
COPY package.json package-lock.json .   # 依赖声明，很少变
RUN npm ci                               # 只要依赖不变，这层就用缓存
COPY . .                                 # 源代码，经常变，放在最后
RUN npm run build

# 差：COPY . . 先执行，改了任何一个文件都会让 npm ci 缓存失效
COPY . .
RUN npm ci
```

## 善用 .dockerignore

在发送构建上下文（build context）给 Docker Daemon 之前，先排除不需要的文件：

```dockerfile
# .dockerignore
node_modules
.git
*.md
dist
.env
Dockerfile
docker-compose.yml
.vscode
.idea
```

**作用**：减小构建上下文体积、避免误将 `node_modules` 或机密文件打进镜像、避免无关文件变动导致缓存失效。

# BuildKit 高级特性

Docker 18.09 引入 BuildKit 作为新一代构建引擎，Docker 23.0 起默认启用。相比旧版 builder，它支持并行构建、更精细的缓存控制、秘密信息挂载等。

如有兼容性问题可手动启用：`DOCKER_BUILDKIT=1 docker build .`

## 缓存挂载（`--mount=type=cache`）

在 `RUN` 指令中挂载一个**跨构建持久化的缓存目录**，避免每次构建重新下载依赖：

```dockerfile
# 包管理器的缓存可以在多次构建间复用
FROM golang:1.21 AS builder
WORKDIR /app
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    go build -o myapp .

# apt 缓存同理
FROM ubuntu:22.04
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update && apt-get install -y nginx
```

缓存目录存储在 BuildKit 守护进程中，不会残留在最终镜像层中。

## 秘密挂载（`--mount=type=secret`）

构建时需要用到密钥（如私有仓库凭证、API token），但**绝不能把密钥写进镜像层**：

```dockerfile
# 构建命令：docker build --secret id=npmrc,src=$HOME/.npmrc .
FROM node:18-alpine
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
# 构建完成后，.npmrc 不会出现在镜像的任何一层中
```

## SSH 挂载（`--mount=type=ssh`）

构建时需要 SSH 私钥来拉取私有 Git 仓库：

```dockerfile
# 构建命令：docker build --ssh default .
FROM golang:1.21
RUN mkdir -p -m 0700 ~/.ssh && ssh-keyscan github.com >> ~/.ssh/known_hosts
RUN --mount=type=ssh \
    go mod download
```

## 并行构建

BuildKit 自动并行构建不相互依赖的阶段，多阶段构建中不同 `FROM` 分支可以同时进行，大幅缩短构建时间。

# 基础镜像选择策略

| 策略 | 镜像 | 典型体积 | 适用场景 |
|:-----|:-----|:---------|:---------|
| Alpine | `alpine:3.18` | ~7MB | 通用场景，使用 musl libc |
| Distroless | `gcr.io/distroless/static` | ~2MB | Go/Rust 等静态编译语言，无 shell |
| Slim | `python:3.11-slim` | ~50MB | 需要 Debian 兼容性但不想带完整系统 |
| Scratch | `FROM scratch` | 0MB | 纯静态二进制，真正最小 |

```dockerfile
# Go 应用的终极版：FROM scratch
FROM golang:1.21 AS builder
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o myapp .

FROM scratch                        # 空镜像，什么都没有
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /app/myapp /
CMD ["/myapp"]
```

`FROM scratch` 镜像里没有 shell、没有包管理器、没有任何工具，攻击面趋近于零。

# 镜像分析工具

- **dive**：交互式查看镜像每一层的内容和体积变化，快速定位膨胀来源
- **docker-slim**：自动分析应用实际用到了哪些文件，剔除所有无用内容
- **hadolint**：Dockerfile 静态分析工具，检查常见陷阱和最佳实践违规

# 优化要点总结

1. **用多阶段构建**：构建与运行分离，只带走编译产物
2. **合并 RUN**：安装和清理在同一层完成，不留残留
3. **按稳定性排序**：最不常变的指令放在最前面，最大化缓存命中
4. **选最小基础镜像**：alpine → distroless → scratch，按需选型
5. **写 .dockerignore**：排除 node_modules、.git、临时文件
6. **用 BuildKit 缓存挂载**：跨构建复用依赖缓存，不在镜像中留痕
7. **秘密信息用 `--mount=type=secret`**：绝不通过 ENV 或 COPY 写入密钥
